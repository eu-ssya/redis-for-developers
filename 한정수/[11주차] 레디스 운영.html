01

Monitoring

프로메테우스 & 그라파나로
레디스 모니터링 구축하기

운영의 출발점은 관찰입니다. Exporter가 메트릭을 노출하면 Prometheus가 끌어와 저장하고, Grafana가 그립니다. 임계치를 넘으면 Alertmanager가 사람에게 알립니다.

1 · 아키텍처

누가 무엇을 수집하는가

Exporter는 대상의 상태를 실시간으로 스크랩해 메트릭으로 노출하는 프로그램입니다. Prometheus는 지정한 타깃(Exporter)에 직접 접근해 pull 방식으로 시계열 데이터를 가져옵니다.

Redis Exporter

지정한 레디스 인스턴스의 실시간 정보(메모리·연결·복제 등)를 수집합니다. 인스턴스마다 1개가 필요합니다.

Node Exporter

레디스가 도는 서버의 하드웨어·OS 메트릭을 수집합니다. 한 서버에 인스턴스가 2개여도 Node Exporter는 1개면 됩니다.

서버 두 대로 짜는 실습 구성

4 · Grafana 대시보드

대시보드를 얻는 두 가지 길

Prometheus를 중간 저장소로 거치는 방식과, Grafana의 Redis 플러그인으로 직결하는 방식이 있습니다. 전자는 과거 시점 그래프를, 후자는 Exporter 없는 실시간 조회를 줍니다.

방식 A · Prometheus 경유

  • 데이터소스에 Prometheus(http://10.0.0.2:9090) 추가

  • 외부에 일정 기간 보관 → 원하는 과거 시점 그래프 조회 가능

레디스를 바로 본다

  • RedisGrafana 플러그인(Redis / Redis Application) 설치
  • 데이터소스에 레디스 주소 직접 입력 (Standalone·Cluster·Sentinel)

  • 온프레미스·클라우드 상품 모두 실시간 대시보드 가능

02

Upgrade

레디스 버전 업그레이드

레디스는 릴리스 주기가 빠르고 EOL이 짧습니다. 버그·보안 취약점을 피하려면 EOL 이전 버전을 유지하도록 주기적으로 올리는 편이 좋습니다.

1 · 두 가지 방법

다운타임을 줄 것인가, 접속 정보를 바꿀 것인가

업그레이드는 크게 둘입니다. 고가용성(Sentinel·Cluster) 구성이면 복제본부터 하나씩 올려 무중단이 가능하고, 싱글 구성이면 둘 중 하나의 비용을 감수해야 합니다.

방법 ①

신규 서버에 설치 후 데이터 복제

새 버전을 새 서버에 올리고 기존 데이터를 복제합니다.

  • 다운타임 없음
  • 대신 애플리케이션의 접속 정보 변경 필요
방법 ②

인스턴스 중지 후 신규 소스로 재실행

실행 중인 인스턴스를 멈추고 새 바이너리로 다시 띄웁니다.

  • 접속 정보 유지
  • 단, 싱글 구성이면 다운타임 발생
v
버전 확인실행 전후로 redis-server --version 또는 접속 후 INFO server(redis_version)로 버전을 확인합니다.

2 · Sentinel 구성

센티널 → 복제본 → 페일오버 → 마스터

핵심 원칙은 “상태 없는 센티널을 먼저, 복제본을 그다음, 마스터는 페일오버 뒤 마지막”입니다. 전 과정에서 다운타임 없이 전체 인스턴스를 올릴 수 있습니다.

1
Sentinel
센티널 3대를 신규 바이너리로 교체
3대 모두 종단 → 기존 sentinel.conf 복사 → 새 바이너리로 시작. 센티널은 상태가 없어 안전합니다.
2
Replica
복제본 인스턴스를 먼저 교체
config rewrite로 설정을 파일에 반영한 뒤 shutdown → 기존 redis.conf 복사 → 새 바이너리로 시작.
3
Failover
수동 페일오버로 역할 교대
sentinel failover mymaster 실행. 기존 마스터에서 INFO replication → role:slave 확인.
4
Master
이제 복제본이 된 기존 마스터를 교체
2단계와 동일하게 중단·설정 복사·재실행. 필요하면 페일오버를 한 번 더 수행해 원래 마스터로 페일백합니다.

3 · Cluster 구성

복제본부터 올리고, 페일오버로 번갈아

클러스터는 센티널 인스턴스를 고려할 필요가 없어 더 간단합니다. 마스터 A·B·C와 그 복제본 D·E·F가 있을 때, 복제본을 먼저 올리고 페일오버로 역할을 바꿔가며 기존 마스터를 올립니다.

3 · 자동 백업 옵션

RDB·AOF는 의도한 시간에만

백업(RDB/AOF)은 운영 인스턴스에 부하를 줍니다. 백그라운드 백업은 COW(Copy-On-Write)로 동작해 메모리가 최대 maxmemory의 2배까지 늘 수 있어, 적절한 maxmemory 없이는 최악의 경우 OOM을 부릅니다.

RDB · save

기본값 3600 1 / 300 100 / 60 10000 = 1시간 1회 · 5분 100회 · 1분 10000회 변경 시 자동 생성.

redis-cli
> CONFIG SET save ""   # 자동 RDB 끄기
OK
AOF · rewrite

auto-aof-rewrite-percentage 100(기존보다 100% 증가 시 재작성) · min-size 64MB(67108864).

redis-cli
> CONFIG SET auto-aof-rewrite-percentage 0
OK   # 자동 재작성 막고 수동 시간에
!
COW 메모리 폭증포그라운드 백업은 메인 스레드를 막아 성능에 영향, 백그라운드 백업은 메모리를 최대 2배까지 사용. 백업은 의도한 시간·인스턴스(가능하면 복제본)에서 수행하도록 설정하세요.

04

Performance

레디스 운영 & 성능 최적화

레디스는 커맨드를 실행하는 동안 싱글 스레드 이벤트 루프로 동작합니다. 하나의 느린 커맨드가 모두를 막는다는 사실이 이 절의 모든 이야기의 전제입니다.

1 · 싱글 스레드의 함정

O(N) 이상의 커맨드를 지양한다

한 번에 하나의 커맨드만 처리하므로, 실행이 길어지면 다른 모든 클라이언트가 대기합니다. 흔한 오해는 KEYS·FLUSHALL만 느리다는 생각인데, set·list·hash 같은 컬렉션 커맨드도 아이템 수에 비례해 느려집니다.

!
지연을 막는 가장 단순한 규칙: 하나의 키 안에 아이템을 너무 많이 담지 않는다. 시간 복잡도의 N은 대개 “그 자료 구조 안의 아이템 개수”입니다.

2 · 커맨드 복잡도 레퍼런스

피해야 할 O(N) 커맨드 지도

자료 구조별로 비용이 큰 커맨드를 모았습니다. 빨강은 전체/곱 비례, 주황은 부분 순회, 초록은 효율적입니다.

3 · Lazy Freeing

DEL은 동기, UNLINK는 비동기

DEL은 메인 스레드에서 동기로 메모리를 해제합니다. 아이템이 수백만인 큰 키는 비동기로 해제하는 UNLINK가 낫습니다. 삭제는 사용자 호출 외에 eviction·만료·RENAME·복제 FLUSH 같은 시스템 상황에서도 일어납니다.

4 · 원자적 실행

트랜잭션 vs 루아 스크립트

둘 다 여러 커맨드를 원자적으로 실행해 중간에 다른 클라이언트의 영향을 차단합니다. 결정적 차이는 롤백입니다 — 트랜잭션은 오류 시 롤백, 루아는 일부가 실패해도 다음으로 진행하며 롤백하지 않습니다.

MULTI / EXEC

큐에 모아 한 번에

  • MULTI → 명령들 QUEUED → EXEC 원자 실행
  • 도중 오류 발생 시 전체 롤백
Lua Script

서버에서 계산, 1회 왕복

  • 원자적이지만 롤백 없음 (트랜잭션과 차이)
  • SCRIPT LOAD → hash → EVALSHA로 재전송 없이 재실행 → 네트워크 절감
!
블로킹 커맨드 금지실행 중 다른 클라이언트가 모두 대기하므로 길이를 짧게. 트랜잭션·스크립트 내부의 BLPOP·BRPOP는 무한 대기를 막기 위해 강제로 차단됩니다 → EXECABORT / ERR ... not allowed from script.

5 · 안티패턴

has-get / has-del 패턴을 버려라

EXISTS로 존재를 확인한 뒤 GET/DEL 하는 패턴은 왕복 2회 + 원자성 붕괴를 부릅니다. 확인과 처리 사이에 다른 클라이언트가 키를 바꿀 수 있고, 애초에 GET은 없으면 nil, DEL은 없어도 에러가 없습니다.

6 · 클라이언트 출력 버퍼

응답을 담는 버퍼, 클래스마다 다르다

client output buffer는 서버 응답을 클라이언트로 보내기 전 임시 저장합니다. 대용량 데이터나 복제 시에는 키워야 하며, client-output-buffer-limit <class> <hard> <soft> <soft seconds>로 설정합니다.

7 · 키스페이스 알림

키 변경·만료를 pub/sub으로 구독

keyspace notification은 내부 pub/sub 채널로 키 변경 사항을 구독하게 해줍니다. notify-keyspace-events에 채널(K/E)과 이벤트 타입 문자를 조합해 지정합니다.

8 · 프리픽스 키 삭제

SCAN+DEL 반복 vs 루아 한 번

레디스는 프리픽스 일괄 삭제를 기본 제공하지 않습니다(마스터에서만 가능). SCAN으로 찾아 삭제하는데, 진짜 비용은 연산이 아니라 네트워크 왕복입니다. 1000만 키 중 100만 개가 매치되면 100만 번의 추가 왕복이 듭니다.

그림 13-14 · 기본 방식

왕복 (A + B)

SCAN ⟳DEL key ⟳

A SCAN을 cursor 0까지 반복 + B 매 키마다 DEL을 반복 → 매치 수만큼 왕복이 누적.

그림 13-15 · 루아 방식

왕복 (A만)

EVALSHA ⟳

스크립트 내부에서 SCAN+DEL을 함께 수행 → DEL 호출 생략, A 횟수만큼만 왕복 → 네트워크 I/O 절감.

⚙
차단 시간은 count로 조절스크립트 실행 중 다른 클라이언트는 차단됩니다. 적절한 배치 크기로 count(예: 1,000)를 조절해 한 번에 처리하는 키 수와 차단 시간을 최소화하세요.

05

Observability

운영 모니터링 지표

안정 운영의 마지막 조각은 “무엇을 볼 것인가”입니다. 느린 커맨드를 기록하는 SlowLog와, 컴퓨팅 자원을 보는 다섯 가지 그래프 지표를 챙깁니다.

1 · 슬로우 로그

느린 커맨드를 메모리에 기록

SlowLog는 실행이 느린 커맨드를 기록합니다. 주기적으로 검토하면 예상치 못한/악의적 명령을 식별해 성능과 보안 모두에 도움이 됩니다.

SLOWLOG GET
> SLOWLOG GET
1) 1) (integer) 1923          # ① 고유 ID
   2) (integer) 1696344048    # ② 실행 시점 (unix timestamp)
   3) (integer) 35233         # ③ 실행 소요 시간 (마이크로초!)
   4) 1) "SCAN"              # ④ 느리게 수행된 커맨드
      2) "10179327"
      3) "COUNT"
      4) "50000"
slowlog-log-slower-than

기록 임계 시간. 마이크로초 단위, 기본 10000 = 10ms.

slowlog-max-len

유지 레코드 수. 기본 128개, 초과 시 오래된 레코드부터 대체.

✎
정확도 메모 — 책 본문 보정책은 “기본은 10,000ms, 즉 10초”라고 적었지만, slowlog-log-slower-than과 SLOWLOG 레코드의 ③ 실행 시간은 밀리초(ms)가 아니라 마이크로초(μs) 단위입니다. 따라서 기본값 10000은 10초가 아니라 10ms입니다. (Redis 공식 문서 기준 확인)

2 · 그래프 지표

다섯 가지 운영 대시보드 지표

자원의 과다 사용은 높은 지연을, 과소 사용은 낭비를 뜻합니다. CPU·메모리·네트워크·커넥션·복제를 꾸준히 지켜봐야 합니다.

🔴 CPU

  • 커맨드 실행은 싱글 스레드, 백업·UNLINK는 다른 CPU 활용
  • O(N) 커맨드·높은 카디널리티 = 부하 ↑
  • 읽기 부하면 복제본 참조로, 백업은 복제본에서

🔵 메모리

  • used_memory(논리) vs used_memory_rss(물리)
  • 둘의 차 = 단편화 → activedefrag(4.0+)로 관리
  • DatabaseMemoryUsagePercentage 100% → eviction (과도하면 CPU↑)

🟢 네트워크

  • 네트워크 I/O 모니터 — VM·도커·k8s의 대역폭 한계 주의
  • 한계에 걸리면 처리량이 더 안 오르는 병목 발생
  • 읽기면 복제본 추가, 쓰기면 마이그레이션·클러스터로 분산

🟠 커넥션

  • 활성·신규 연결 수 추이 주시 (급증 = 누수 의심)
  • tcp-keepalive(기본 300초)로 유휴 연결 정리
  • 연결 비용이 큼 → 커넥션 풀링, TLS 핸드셰이크 비용 유의

🟣 복제

마스터는 복제본이 있으면 명령 스트림을 계속 전송합니다. 복제 지연(replication lag)의 급증은 복제본이 마스터 속도를 못 따라간다는 신호입니다. 지연이 커지면 복제본이 전체 동기화를 요청할 수 있고, 이때 마스터가 스냅숏을 만들며 성능이 저하됩니다. 원인은 마스터의 과도한 쓰기, 네트워크 대역폭 고갈, 복제 출력 버퍼 크기 문제 등이므로 다른 메트릭과 함께 점검합니다.
