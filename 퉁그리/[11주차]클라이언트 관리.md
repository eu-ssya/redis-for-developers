# 개발자를 위한 레디스 12장 학습 정리

레디스가 클라이언트 연결을 처리하고 관리하는 방법을 다룬 챕터다. 책 359–376쪽이 범위다.

레디스는 단일 스레드로 수많은 클라이언트의 요청을 동시에 받아낸다. 12장은 그 연결이 어떻게 수락되고(핸들링), 메모리를 과하게 먹지 않도록 어떻게 제한되며(버퍼와 이빅션), 유휴 연결을 어떻게 정리하는지(타임아웃)를 먼저 보고, 이어서 클라이언트 쪽에서 성능을 끌어올리는 두 기법인 **파이프라이닝**과 **클라이언트 사이드 캐싱**을 살펴본다. 앞쪽은 "서버가 연결을 어떻게 지키는가", 뒤쪽은 "클라이언트가 왕복 시간을 어떻게 줄이는가"로 묶어 읽으면 좋다.

## 1. 클라이언트 핸들링

**연결 수단.** 레디스는 클라이언트 연결을 받는 데 TCP 포트와 유닉스 소켓을 쓸 수 있다. 보통은 TCP 포트를 쓰지만, 설정 파일에서 `unixsocket`/`unixsocketperm`을 지정하면 원하는 경로에 소켓 파일을 만들고 권한을 부여할 수 있다.

```
unixsocket /tmp/redis.sock
unixsocketperm 777
```

이후 클라이언트는 그 소켓 경로로 접속한다(`redis-cli -s /tmp/redis.sock`).

**멀티플렉싱과 논블로킹 I/O.** 레디스는 멀티플렉싱(multiplexing) 방식을 쓴다. 하나의 스레드에서 여러 소켓을 감시하다가 소켓 이벤트가 발생하는지 지속적으로 확인하므로, 다수의 클라이언트를 블로킹 없이 동시에 처리할 수 있다. 여기에 논블로킹 I/O를 더해, I/O 작업이 끝날 때까지 기다리지 않고 다른 작업을 처리하면서 요청을 비동기적으로 다룬다.

**TCP_NODELAY.** 레디스는 클라이언트 커넥션을 만들 때 `TCP_NODELAY` 옵션을 켠다. 이 옵션은 작은 데이터라도 버퍼링하지 않고 지연 없이 곧바로 패킷으로 내보내, 연결 지연을 최소화한다. 소스 코드(`redis/src/networking.c`)에서 클라이언트를 생성할 때 이 옵션을 활성화하는 것을 볼 수 있다.

```c
client *createClient(connection *conn) {
    client *c = zmalloc(sizeof(client));
    if (conn) {
        connEnableTcpNoDelay(conn);              // TCP_NODELAY 활성화
        if (server.tcpkeepalive)
            connKeepAlive(conn, server.tcpkeepalive);
        connSetReadHandler(conn, readQueryFromClient);
        connSetPrivateData(conn, c);
    }
    ...
}
```

> **NOTE: 클라이언트 통신은 못 끄지만, 복제 연결은 끌 수 있다**
> 레디스 버전 7 기준, 레디스와 클라이언트 사이 통신의 `TCP_NODELAY`는 해제할 수 없다. 하지만 노드 간 복제 연결에서는 `repl-disable-tcp-nodelay yes`로 끌 수 있다. `yes`로 두면 복제본에 데이터를 보낼 때 더 적은 TCP 패킷과 대역폭을 쓰지만, 복제본에 데이터가 나타나기까지 최대 40밀리초가량 지연될 수 있다. 기본값은 지연을 최소화하기 위한 `no`이며, 대규모 트래픽이거나 마스터-복제본 간 거리가 멀 때 `yes`가 도움이 될 수 있다.

**maxclients.** 클라이언트가 초기화되면 레디스는 현재 연결 수가 `maxclients`에 도달했는지 확인하고, 초과하면 새 접속을 거부한다. 버전 2.6부터 기본값은 10,000이다. 단 레디스는 시작할 때 OS의 파일 디스크립터 한계도 함께 본다. 내부적으로 32개의 파일 디스크립터를 예약하므로, `maxclients + 32`보다 OS의 파일 디스크립터 수가 작으면 `maxclients`를 OS에 맞춰 낮춰서 시작한다.

## 2. 클라이언트 버퍼 제한

레디스는 클라이언트마다 반환할 데이터를 임시로 담아두는 **클라이언트 출력 버퍼(client output buffer)**를 둔다. 연결된 클라이언트가 1,000개면 출력 버퍼도 1,000개다. 클라이언트가 데이터를 제때 못 받아가면 출력 버퍼가 계속 커져 메모리 사용량이 늘어난다. 특히 pub/sub은 발행 속도를 구독자가 못 따라가는 경우가 많다. 그래서 레디스는 출력 버퍼에 제한을 두고, 일정 수준을 넘으면 그 연결을 끊는다.

- **하드 제한**: 고정값. 도달하면 즉시 연결을 닫는다.
- **소프트 제한**: 시간 조건이 붙은 제한. 예를 들어 "10초 동안 지속적으로 32MB를 초과"하면 연결을 닫는다.

클래스(클라이언트 종류)마다 기본 제한이 다르다.

| 클래스 | 하드 제한 | 소프트 제한 | 이유 |
|---|---|---|---|
| `normal` (일반) | 0 (무제한) | 0 | 커맨드를 보내고 응답을 기다리는 구조라, 임의로 끊으면 예상치 못한 동작이 됨 |
| `pubsub` | 32MB | 60초당 8MB | 빠르게 쏟아지는 메시지를 처리하려면 더 많은 메모리가 필요 |
| `slave`(replica) | 256MB | 60초당 64MB | 마스터로부터 대량의 데이터를 받으므로 더 큰 버퍼가 필요 |

설정은 파일 또는 `CONFIG SET`으로 바꾼다.

```
CONFIG SET client-output-buffer-limit <class> <hard-limit> <soft-limit> <soft-limit-duration>
# 예: 복제 클라이언트의 제한을 모두 제거
CONFIG SET client-output-buffer-limit "slave 0 0 0"
```

`<class>`는 `normal`/`slave`(`replica`)/`pubsub` 중 하나이고, 하드 제한과 소프트 제한은 바이트, 소프트 제한 지속 시간은 초 단위다.

출력 버퍼와 별개로 **클라이언트 쿼리 버퍼(client query buffer)**도 있다. 출력 버퍼가 서버→클라이언트 응답용이라면, 쿼리 버퍼는 클라이언트가 보낸 커맨드를 레디스가 처리 전 잠시 보관하는 버퍼다. 기본 크기는 1GB로, 클라이언트 버그로 쿼리 버퍼가 무한정 커지는 것을 막기 위한 안전장치다. 특별한 경우 `client-query-buffer-limit`로 조정한다.

## 3. 클라이언트 이빅션

클라이언트 연결 수가 늘면 그만큼 메모리도 늘어, 연결이 OOM(Out Of Memory)을 일으키거나 데이터 이빅션을 유발할 수 있다. 예전에는 연결 메모리와 데이터 메모리를 통합해 `maxmemory-policy`로 관리했지만, 레디스 7.0부터는 **`maxmemory-clients`**로 모든 클라이언트 연결(일반+pub/sub)이 쓰는 누적 메모리를 따로 제한할 수 있다. 임계치에 도달하면 레디스는 **가장 많은 메모리를 쓰는 연결부터** 끊어 메모리를 확보하는데, 이를 **클라이언트 이빅션(client eviction)**이라 한다. 이 계산에는 쿼리 버퍼, 출력 버퍼, 중간 버퍼가 모두 포함되며, 임계치를 넘지 않을 만큼만 최소한으로 연결을 해제한다.

```
maxmemory-clients 1G    # 절대 크기
maxmemory-clients 5%    # maxmemory의 5%
```

기본값은 `0`(비활성)이다. 대규모 트래픽 환경에서는 `5%`나 `10%` 같은 값이 권장된다. 단 **복제본과 마스터 커넥션은 이빅션 대상이 아니므로**, 복제에 메모리를 아무리 많이 써도 이 설정으로 끊기지 않는다.

특정 연결을 이빅션에서 빼고 싶을 때(예: 주기적으로 모니터링과 알림을 보내는 애플리케이션)는 그 클라이언트에서 `CLIENT NO-EVICT on`을 실행하면 강제로 끊기지 않으며, `off`로 되돌릴 수 있다.

## 4. Timeout과 TCP Keepalive

연결은 한동안 커맨드를 안 보내도 계속 유지된다. 활동 없는 연결을 정리하는 수단이 둘 있다.

**timeout.** 유휴 연결을 해제하는 설정이다. `redis.conf`나 `CONFIG SET timeout <초>`로 지정하면, 그 시간 동안 활동이 없는 클라이언트 연결을 끊는다. 클라이언트 소프트웨어 버그로 유휴 연결이 쌓여 장애가 나는 상황을 막아준다. 기본값은 `0`이라 끄지 않으며, **pub/sub 클라이언트에는 영향을 주지 않는다.**

```
CONFIG SET timeout 600
```

**tcp-keepalive.** 연결된 클라이언트에게 주기적으로 TCP ACK를 보내고, 응답이 없으면 연결을 끊는 설정이다. `timeout`이 "활동 없으면 무조건 끊는" 것과 달리, `tcp-keepalive`는 클라이언트가 실제로 응답 가능한 상태인지 먼저 확인한 뒤 응답하지 않을 때만 끊는다. 정기적으로 ACK를 주고받으면 중간 네트워크 장비가 연결을 살아 있는 것으로 인식해, 장비로 인한 예기치 않은 연결 종료를 막고 네트워크 문제를 조기에 감지할 수 있다. 버전 3.2.0부터 기본값은 300초(5분)라, 서버는 5분마다 한 번 TCP ACK를 보낸다.

## 5. 파이프라이닝

레디스 서버와 클라이언트는 네트워크로 연결돼 있어, 요청과 응답 사이의 **왕복 시간(RTT, Round Trip Time)**이 성능을 크게 좌우한다. 서버가 초당 10만 개를 처리할 수 있어도, 왕복 시간이 250ms라면 한 번에 하나씩 주고받는 방식으로는 초당 4개밖에 처리하지 못한다. 즉 처리량의 병목이 서버 연산이 아니라 네트워크 왕복에 있다.

**파이프라이닝(pipelining)**은 클라이언트가 응답을 기다리지 않고 여러 커맨드를 연속으로 보내는 기능이다. 한 번의 왕복으로 여러 커맨드를 처리하므로 응답 지연을 줄이고 처리량을 늘린다. 가장 단순하게는 줄바꿈으로 구분한 커맨드를 한꺼번에 보내면 된다.

```
$ (printf "PING\r\nPING\r\nPING\r\n"; sleep 1) | nc localhost 6379
+PONG
+PONG
+PONG
```

클라이언트 라이브러리를 쓰면 더 직관적이다. 파이썬 `redis-py`에서는 `pipeline()` 객체에 커맨드를 쌓은 뒤 `execute()`로 한 번에 실행한다.

```python
r = redis.Redis(host='localhost', port=6379)

pipeline = r.pipeline()        # 파이프라인 시작
pipeline.set('name', 'redis')  # 여러 커맨드를 파이프라인에 추가
pipeline.incr('counter')
pipeline.get('name')
results = pipeline.execute()   # 한 번에 실행
```

**왜 빨라지는가.** 레디스가 소켓 I/O를 할 때 커널의 `read()`/`write()` 시스템 콜을 호출하는데, 이 레이턴시가 데이터를 찾아 반환하는 시간보다 크다. 파이프라이닝을 쓰면 여러 커맨드가 단일 `read()`로 읽히고 여러 응답이 단일 `write()`로 나가, 시스템 콜 횟수가 줄어든다. 그래서 파이프라인에 커맨드가 많아질수록 초당 처리 쿼리 수가 거의 선형적으로 늘어난다.

**성능 비교.** 책은 약 1,200만 개의 키를 순회하며 각 키의 타입과 메모리 사용량을 조회하는 작업을 두 방식으로 측정한다. 키를 `SCAN`으로 가져온 뒤 `TYPE`과 `MEMORY USAGE`를 키마다 하나씩 호출하는 방식과, 같은 호출을 배치 단위로 파이프라인에 쌓아 실행하는 방식이다.

| 방식 | 소요 시간 |
|---|---|
| 키마다 개별 호출 | 약 4시간 20분 |
| 파이프라인(배치) | 약 3분 33초 |

알고리듬은 그대로 두고 데이터 수집만 파이프라인으로 바꿨을 뿐인데 **약 142배** 빨라졌다. 처리량 그래프(그림 12-2)로 보면, 개별 호출은 4시간 동안 평균 800개/구간의 커맨드를 처리한 반면, 파이프라인은 4분도 안 되는 시간에 평균 66,000개/구간을 처리했다.

**주의점.** 파이프라이닝이 항상 좋은 건 아니다.

- 한 번에 너무 많은 쿼리를 보내면 네트워크 대역폭 한계로 오히려 느려지고, 클라이언트 쿼리 버퍼 제한(기본 1GB)에 걸려 오류가 날 수 있다. 그래서 10만 개씩 보내고 응답을 받은 뒤 다음 10만 개를 보내는 식으로 **배치 크기를 나눠** 처리하는 것이 좋다. 처리 속도는 거의 같으면서 서버 메모리를 아껴 쓴다. 적절한 배치 크기는 데이터 종류와 크기에 따라 다르므로 테스트로 결정한다.
- **파이프라인은 원자성을 보장하지 않는다.** 트랜잭션이 아니다. 여러 커맨드를 한꺼번에 보낼 뿐, 다른 클라이언트의 접근을 차단하지 않아 명령들이 다른 연결과 교차로 수행될 수 있다(그림 12-3). 또한 파이프라인 내 일부 커맨드에서 오류가 나도 전체가 롤백되지 않고, 오류 난 커맨드만 실행되지 않을 뿐 나머지는 정상 수행된다.

## 6. 클라이언트 사이드 캐싱

버전 6에서 추가된 기능으로, 파이프라이닝과 같은 문제의식, 즉 **왕복 시간을 줄이자**는 데서 출발한다. 쿼리가 들어올 때마다 레디스에 요청하는 대신, 자주 쓰는 쿼리의 응답을 **클라이언트(애플리케이션) 로컬 메모리에 캐싱**해두고 재사용한다. 네트워크를 타지 않으므로 응답 시간이 크게 줄고, 레디스에 접근하지 않으니 서버 부하도 준다. 레디스처럼 빠른 캐시를 쓰는데도 만족스러운 성능이 안 나올 때 추가로 고려해볼 수 있다.

데이터셋의 아이템이 자주 변하지 않을 때 합리적이다. 예를 들어 SNS에 한 번 올린 게시물은 잘 바뀌지 않고, 팔로워가 많은 사용자 구조에서는 같은 데이터를 반복 조회하므로 캐싱 효과가 크다.

다만 모든 캐싱이 그렇듯 **정합성**(원본이 바뀌면 캐시를 어떻게 갱신할 것인가)이 문제다. 레디스는 이를 **트래킹(tracking)**으로 처리하며 두 가지 모드를 제공한다.

| 모드 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **기본 모드** (Default) | 서버가 클라이언트가 접근한 키를 기억했다가, 그 키가 수정되면 무효화 메시지를 보냄 | 클라이언트가 실제로 가진 키에 대해서만 정확히 무효화 | 서버가 키를 기억해야 하므로 메모리 비용이 큼 |
| **브로드캐스팅 모드** (Broadcasting) | 서버가 모든 키 접근을 기억하지 않고, 특정 프리픽스에 접근한 클라이언트만 기억. 그 프리픽스의 키가 바뀌면 해당 클라이언트들에 변경 메시지를 보냄 | 서버 메모리 사용이 적음 | 클라이언트가 직접 프리픽스를 기억해야 하고, 자신이 안 가진 키라도 프리픽스만 맞으면 메시지를 받아 서버 CPU를 소비 |

캐싱 모드는 서비스 특성에 맞게 신중히 골라야 하며, **자주 요청되지만 드물게 변경되는 키**를 캐싱할 때 효과가 가장 크다.

## 헷갈리기 쉬운 지점

- **출력 버퍼 vs 쿼리 버퍼.** 출력 버퍼는 서버→클라이언트 응답을 담고(클래스별 제한, pub/sub과 복제본이 더 큼), 쿼리 버퍼는 클라이언트→서버 커맨드를 처리 전 담는다(기본 1GB). 방향이 반대다.
- **normal 클라이언트의 출력 버퍼 제한은 기본 0(무제한).** 일반 클라이언트는 요청-응답을 번갈아 하므로 버퍼가 폭주할 일이 적고, 함부로 끊으면 예상 밖 동작이 되기 때문이다. 반대로 pub/sub과 복제본은 데이터가 한쪽으로 쏟아져 제한이 걸려 있다.
- **maxmemory-clients는 복제 연결을 제외한다.** 클라이언트 이빅션은 일반과 pub/sub 연결만 대상으로 하며, 마스터-복제본 커넥션은 메모리를 많이 써도 이 설정으로 끊기지 않는다.
- **timeout vs tcp-keepalive.** `timeout`은 "유휴 시간이 지나면 무조건 끊는다"(기본 0, pub/sub 제외). `tcp-keepalive`는 "ACK로 살아 있는지 먼저 확인하고, 응답 없을 때만 끊는다"(기본 300초). 전자는 유휴 정리, 후자는 죽은 연결 감지와 네트워크 유지가 목적이다.
- **파이프라이닝 ≠ 트랜잭션.** 여러 커맨드를 한 번에 보내 왕복을 줄일 뿐, 원자성도 격리성도 없다. 중간 오류가 나도 롤백되지 않고, 다른 클라이언트 명령과 교차 실행될 수 있다. 원자성이 필요하면 `MULTI`/`EXEC`나 Lua 스크립트를 써야 한다.
- **클라이언트 사이드 캐싱의 두 모드는 "무엇을 서버가 기억하느냐"가 다르다.** 기본 모드는 서버가 키별 접근을 기억(정확하지만 서버 메모리↑), 브로드캐스팅 모드는 프리픽스만 기억(서버 메모리↓이지만 불필요한 무효화 메시지로 CPU와 트래픽↑). 정확성을 살 것인가 서버 메모리를 아낄 것인가의 트레이드오프다.
- **파이프라이닝과 클라이언트 사이드 캐싱은 같은 적(왕복 시간)을 다르게 친다.** 파이프라이닝은 "왕복 횟수를 묶어서 줄이고", 캐싱은 "아예 왕복을 안 하게" 만든다.

> 본문의 성능 수치(약 4시간 20분 → 3분 33초, 약 142배, 처리량 800 → 66,000)와 평균 메모리 사용량은 책 저자의 특정 환경과 데이터셋에서 측정된 참고치다. `maxclients`(기본 10,000), 버퍼 기본값(pubsub 32MB, replica 256MB), `tcp-keepalive`(기본 300초) 같은 값은 레디스 버전에 따라 달라질 수 있다.
