## 클라이언트 관리

### 클라이언트 핸들링

Redis는 클라이언트 연결을 수락하기 위해 TCP 포트와 유닉스 소켓을 사용할 수 있다. 일반적인 클라이언트 연결은 TCP 포트를 사용하지만, 같은 서버 안에서 Redis와 애플리케이션이 통신하는 경우 유닉스 소켓을 사용할 수 있다. 유닉스 소켓은 네트워크 스택을 거치지 않고 파일 경로를 통해 통신하므로 로컬 통신에서 사용할 수 있는 선택지다.

#### TCP 포트와 유닉스 소켓

유닉스 소켓은 `redis.conf`에서 소켓 파일 경로와 권한을 지정해 활성화한다.

```conf
unixsocket /tmp/redis.sock
unixsocketperm 777
```

Redis를 시작하면 지정한 경로에 소켓 파일이 생성되고, 클라이언트는 해당 파일 경로를 사용해 Redis 서버에 연결한다.

```bash
redis-cli -s /tmp/redis.sock
```

- **TCP 포트** — 네트워크를 통해 Redis에 접속할 때 사용하는 일반적인 연결 방식이다.
- **유닉스 소켓** — 같은 서버 내부에서 파일 경로를 통해 Redis에 접속하는 방식이다.
- **`unixsocket`** — Redis가 생성할 유닉스 소켓 파일 경로를 지정한다.
- **`unixsocketperm`** — 생성된 소켓 파일의 접근 권한을 지정한다.

#### Multiplexing

Redis는 Multiplexing 방식으로 여러 클라이언트 연결을 처리한다. 하나의 스레드에서 여러 소켓을 감시하고, 각 소켓에 읽기나 쓰기 이벤트가 발생했는지 확인한다. 이 방식은 하나의 통신 채널만 처리하는 구조가 아니라 여러 클라이언트의 요청을 이벤트 기반으로 처리하는 구조다.

Multiplexing을 사용하면 많은 클라이언트 요청을 동시에 처리할 수 있고, 특정 소켓에서 응답을 기다리는 동안 전체 서버가 멈추는 상황을 줄일 수 있다.

#### Non-blocking I/O

Redis는 Non-blocking I/O를 사용한다. I/O 작업이 완료될 때까지 대기하지 않고, 처리 가능한 다른 작업을 계속 수행한다. 이 구조는 클라이언트 요청을 비동기적으로 다루는 데 유리하다.

클라이언트가 보낸 데이터가 도착하면 Redis는 읽기 가능한 파일 이벤트를 생성하고, 해당 이벤트를 통해 클라이언트 쿼리를 수집해 처리한다.

#### TCP_NODELAY

Redis는 클라이언트 커넥션을 생성할 때 `TCP_NODELAY` 옵션을 사용한다. 이 옵션은 작은 데이터라도 버퍼링하지 않고 가능한 한 빠르게 패킷으로 전송하도록 한다. Redis 요청과 응답은 작은 데이터 조각으로 오가는 경우가 많으므로, `TCP_NODELAY`는 클라이언트 연결 지연을 줄이는 데 사용된다.

Redis 소스 코드의 클라이언트 생성 흐름에는 `connEnableTcpNoDelay(conn)` 호출이 포함된다. 이 호출은 클라이언트 커넥션에 `TCP_NODELAY`를 적용한다.

> **참고:** Redis 7 기준으로 Redis와 일반 클라이언트가 통신할 때 `TCP_NODELAY` 옵션을 해제할 수 없다. 하지만 마스터와 복제본 간 복제 연결에서는 다음 설정으로 전송 방식을 조정할 수 있다.

```conf
repl-disable-tcp-nodelay yes
```

`repl-disable-tcp-nodelay`를 `yes`로 설정하면 복제본으로 데이터를 전송할 때 더 적은 수의 TCP 패킷을 사용한다. 하지만 데이터가 복제본에 반영되기까지 최대 약 40ms 수준의 지연이 발생할 수 있다. 이 값을 `no`로 두면 마스터와 복제본 간 데이터 지연을 줄일 수 있지만, 복제 트래픽이 더 많은 대역폭을 사용할 수 있다.

#### maxclients

Redis는 새 클라이언트가 연결될 때 현재 클라이언트 수가 `maxclients` 값에 도달했는지 확인한다. 초과한 경우 Redis는 새 클라이언트 접속을 거부한다.

Redis 2.6 이후 기본 `maxclients` 값은 10000이다. 하지만 실제 허용 가능한 클라이언트 수는 운영체제의 파일 디스크립터 제한에도 영향을 받는다. Redis 서버는 내부적으로 파일 디스크립터 일부를 예약하므로, 설정한 `maxclients` 값에 추가 여유분이 필요하다.

- **설정값** — `maxclients`는 Redis가 동시에 받을 수 있는 클라이언트 연결 수를 제한한다.
- **운영체제 제한** — 파일 디스크립터 제한이 낮으면 Redis가 설정값보다 작은 클라이언트 수만 허용할 수 있다.
- **접속 거부** — 한계에 도달하면 새 클라이언트 연결은 거부된다.

#### 클라이언트 출력 버퍼

Redis는 클라이언트에게 반환할 데이터를 임시 저장하기 위해 각 클라이언트마다 출력 버퍼를 생성한다. 출력 버퍼는 Redis가 클라이언트로 보내야 할 응답을 잠시 보관하는 공간이다.

클라이언트가 응답을 빠르게 읽지 못하면 출력 버퍼가 계속 커지고, Redis 서버의 메모리 사용량도 증가한다. pub/sub 클라이언트에서는 이 문제가 더 쉽게 발생할 수 있다. 발행자가 메시지를 보내면 Redis는 메시지를 모든 구독자에게 전달해야 하지만, 느린 구독자는 메시지를 충분히 빠르게 소비하지 못할 수 있다.

Redis는 출력 버퍼 증가를 제한하기 위해 클라이언트 유형별 하드 제한과 소프트 제한을 제공한다.

| 클라이언트 유형 | 하드 제한 | 소프트 제한 |
|---|---:|---:|
| 일반 클라이언트 | 제한 없음 | 제한 없음 |
| pub/sub 클라이언트 | 32MB | 8MB, 60초 |
| 복제본 클라이언트 | 256MB | 64MB, 60초 |

- **하드 제한** — 출력 버퍼가 즉시 기준값에 도달하면 Redis가 가능한 한 빨리 연결을 닫는다.
- **소프트 제한** — 출력 버퍼가 기준값을 일정 시간 동안 초과하면 Redis가 연결을 닫는다.
- **일반 클라이언트** — 기본적으로 출력 버퍼 제한이 0으로 설정되어 제한을 두지 않는다.

#### client-output-buffer-limit

출력 버퍼 제한은 `redis.conf`에서 설정하거나 `CONFIG SET`으로 변경할 수 있다.

```redis
CONFIG SET client-output-buffer-limit <class> <hard-limit> <soft-limit>
<soft-limit-duration>
```

`<class>`에는 `normal`, `slave`, `replica`, `pubsub` 중 하나를 지정한다. `normal`은 일반 Redis 클라이언트, `slave`와 `replica`는 복제본 클라이언트, `pubsub`은 pub/sub 클라이언트를 의미한다.

복제 클라이언트의 제한을 제거하는 예시는 다음과 같다.

```redis
> CONFIG SET client-output-buffer-limit "slave 0 0 0"
OK
```

> **참고:** 최신 Redis 문서에서는 복제본을 `replica`라고 표현하지만, 설정과 호환성을 위해 `slave` 표현도 함께 남아 있다. 책의 예시는 `slave`를 사용한다.

#### 클라이언트 쿼리 버퍼

클라이언트 출력 버퍼와 별도로 클라이언트 쿼리 버퍼가 존재한다. 쿼리 버퍼는 클라이언트가 Redis 서버에 보낸 커맨드를 Redis가 처리하기 전 잠시 보관하는 내부 버퍼다.

클라이언트 쿼리 버퍼는 기본적으로 1GB로 제한된다. 이 제한은 클라이언트 버그나 비정상 동작으로 인해 쿼리 버퍼가 무한히 증가하는 상황을 막기 위한 장치다. 특수한 상황에서는 `client-query-buffer-limit` 설정으로 크기를 조정할 수 있다.

#### 클라이언트 이빅션

클라이언트 연결 수가 많아지면 클라이언트 연결 자체가 상당한 메모리를 사용할 수 있다. 이전 버전에서는 클라이언트 연결과 데이터 저장에 사용하는 메모리를 통합해 `maxmemory-policy`로 관리했다. Redis 7.0부터는 `maxmemory-clients` 설정으로 클라이언트 연결이 사용하는 메모리 합계를 별도로 제한할 수 있다.

`maxmemory-clients` 임계치에 도달하면 Redis는 가장 많은 메모리를 사용하는 클라이언트 연결부터 해제해 메모리를 확보한다. 이 기능을 클라이언트 이빅션이라고 한다.

```conf
maxmemory-clients 1G
maxmemory-clients 5%
```

- **바이트 단위 지정** — `1G`처럼 특정 크기를 직접 지정한다.
- **퍼센트 지정** — `5%`처럼 `maxmemory` 값의 일정 비율로 지정한다.
- **기본값** — 기본값은 0이며, 클라이언트 이빅션 기능이 비활성화된 상태를 의미한다.
- **복제 연결** — 복제본과 마스터 사이의 복제 연결은 클라이언트 이빅션에 의해 자동으로 끊기지 않는다.

대규모 트래픽 환경에서는 클라이언트 연결이 사용하는 메모리를 제한하기 위해 5%나 10% 같은 값을 설정하는 것이 권장된다.

#### CLIENT NO-EVICT

특정 클라이언트 연결은 클라이언트 이빅션 대상에서 제외할 수 있다. Redis 서버를 주기적으로 모니터링하거나 알림을 보내는 애플리케이션은 강제로 연결이 끊기지 않도록 설정할 수 있다.

```redis
> CLIENT NO-EVICT on
OK
```

이 명령을 실행한 클라이언트는 클라이언트 이빅션 대상에서 제외된다. 설정을 되돌리려면 다음 명령을 사용한다.

```redis
> CLIENT NO-EVICT off
OK
```

### Timeout과 TCP Keepalive

#### timeout

클라이언트가 Redis에 연결된 뒤 장기간 커맨드를 수행하지 않아도 연결은 유지된다. 유휴 클라이언트 연결을 정리하려면 `timeout` 값을 설정한다.

```redis
> CONFIG SET timeout 600
OK
```

`timeout`은 지정한 초 동안 아무 활동이 없는 클라이언트 연결을 Redis가 해제하도록 한다. 기본값은 0이며, 기본적으로 유휴 연결을 강제로 종료하지 않는다는 의미다. pub/sub 클라이언트는 연결이 오래 유지되는 구조이므로 `timeout`의 영향을 받지 않는다.

#### tcp-keepalive

`tcp-keepalive`는 연결된 클라이언트에게 주기적으로 TCP ACK를 보내고, 클라이언트로부터 응답이 없으면 연결을 끊는 설정이다. `timeout`이 클라이언트 활동 유무를 기준으로 연결을 정리한다면, `tcp-keepalive`는 클라이언트가 실제로 응답 가능한 상태인지 확인한다.

`tcp-keepalive`는 네트워크 장비가 유휴 연결을 예기치 않게 끊는 상황을 줄이고, 비정상 클라이언트 연결을 조기에 감지하는 데 사용된다. Redis 3.2.0부터 기본값은 300초이며, Redis 서버는 연결된 클라이언트에게 약 5분마다 TCP ACK를 보낸다.

| 설정 | 기준 | 기본값 | pub/sub 영향 |
|---|---|---:|---|
| `timeout` | 클라이언트 유휴 시간 | 0 | 적용되지 않음 |
| `tcp-keepalive` | TCP 응답 가능 여부 | 300초 | 연결 상태 확인에 사용됨 |

### 파이프라이닝

#### 요청-응답 왕복 시간과 처리량

Redis 서버와 클라이언트는 네트워크를 통해 요청과 응답을 주고받는다. 일반적인 방식에서는 클라이언트가 하나의 커맨드를 보내고, 서버가 처리 결과를 반환한 뒤 다음 커맨드를 보낸다. 이 구조에서는 각 커맨드마다 네트워크 왕복 시간인 RTT가 발생한다.

Redis 서버가 초당 많은 명령을 처리할 수 있더라도 RTT가 크면 실제 클라이언트 처리량은 낮아질 수 있다. 예를 들어 RTT가 250ms라면 서버 처리 능력과 관계없이 단일 요청-응답 방식에서는 초당 처리 가능한 명령 수가 크게 제한된다.

#### 파이프라이닝 동작 방식

파이프라이닝은 클라이언트가 여러 커맨드를 연속으로 Redis 서버에 보내고, 응답을 나중에 모아서 받는 방식이다. 각 커맨드마다 응답을 기다리지 않으므로 RTT 영향을 줄일 수 있다.

- **일반 방식** — 커맨드 하나를 보내고 응답을 받은 뒤 다음 커맨드를 보낸다.
- **파이프라이닝 방식** — 여러 커맨드를 한 번에 보내고 여러 응답을 이어서 받는다.
- **성능 효과** — 네트워크 왕복 횟수를 줄이고 `read()`와 `write()` 시스템 콜 횟수도 줄인다.

파이프라이닝에 포함된 커맨드가 많아질수록 초당 처리되는 쿼리 수는 크게 증가할 수 있다. 하지만 한 번에 너무 많은 커맨드를 보내면 네트워크 대역폭, Redis 클라이언트 쿼리 버퍼, 클라이언트 측 메모리 사용량이 병목이 될 수 있다.

#### redis-cli와 nc를 이용한 예시

파이프라이닝은 Redis 프로토콜에 맞는 여러 커맨드를 한 번에 보내는 방식으로 확인할 수 있다.

```bash
$ (printf "PING\r\nPING\r\nPING\r\n"; sleep 1) | nc localhost 6379
+PONG
+PONG
+PONG
```

세 개의 `PING` 커맨드를 한 번에 보내고, 한 번의 왕복 시간 안에서 세 개의 응답을 받는다.

#### redis-py pipeline 예시

Redis 클라이언트 라이브러리를 사용하면 파이프라이닝을 더 직관적으로 사용할 수 있다. redis-py에서는 `pipeline()`을 생성한 뒤 여러 명령을 추가하고 `execute()`로 실행한다.

```python
import redis

# Redis 서버에 연결
r = redis.Redis(host='localhost', port=6379)

# Pipeline 시작
pipeline = r.pipeline()

# 여러 개의 명령을 Pipeline에 추가
pipeline.set('name', 'Redis')
pipeline.incr('counter')
pipeline.get('name')

# Pipeline 실행
results = pipeline.execute()
```

> **주의:** 책 사진의 예시에서는 실행 변수명이 `pipe.execute()`처럼 보이지만, 앞에서 생성한 변수명은 `pipeline`이다. 실행 가능한 코드로는 `pipeline.execute()`가 맞다.

#### 파이프라이닝 성능 비교

책의 테스트는 Redis에 저장된 약 1200만 개의 키를 대상으로 각 키의 타입과 메모리 사용량을 조회한다. 첫 번째 방식은 `SCAN`으로 키를 가져온 뒤 각 키마다 `TYPE`과 `MEMORY USAGE`를 순차 실행한다.

순차 실행 결과는 다음과 같다.

```text
Type: 'string', Count: 6197600
Type: 'set', Count: 36922
Type: 'zset', Count: 48
Type: 'hash', Count: 1
Type: 'list', Count: 1
Average Memory Usage: 754.1511653085408 bytes

real    265m2.968s
user    15m12.969s
sys     6m36.587s
```

파이프라이닝 적용 후 결과는 데이터 집계값은 동일하지만 실행 시간이 크게 줄어든다.

```text
Type: 'string', Count: 6197600
Type: 'set', Count: 36922
Type: 'zset', Count: 48
Type: 'hash', Count: 1
Type: 'list', Count: 1
Average Memory Usage: 754.1511653085408 bytes

real    3m33.937s
user    3m25.115s
sys     0m1.669s
```

| 방식 | 처리 시간 | 특징 |
|---|---:|---|
| 순차 실행 | 약 265분 | 각 키마다 개별 커맨드 왕복이 발생한다 |
| 파이프라이닝 | 약 3분 33초 | 여러 커맨드를 배치로 묶어 RTT와 시스템 콜 비용을 줄인다 |

같은 장비와 같은 Redis 인스턴스에서 데이터 수집 알고리듬은 유지하고 파이프라인만 적용했을 때, 작업 시간이 약 142배 줄어든다.

#### 배치 크기 조정

파이프라이닝을 사용할 때는 한 번에 보낼 커맨드 수를 조절해야 한다. 너무 많은 커맨드를 한 번에 보내면 네트워크 대역폭을 과도하게 사용하거나 Redis 클라이언트 쿼리 버퍼 제한에 걸릴 수 있다. 클라이언트 쪽에서도 응답을 저장하기 위한 메모리 사용량이 증가할 수 있다.

배치 크기는 데이터 타입과 값 크기에 따라 달라진다. 책의 테스트 코드에서는 `batch_size = 50000`으로 설정하고, 키마다 `TYPE`과 `MEMORY USAGE`를 파이프라인에 추가한 뒤 배치 단위로 실행한다.

- **작은 배치** — 메모리 부담은 작지만 RTT 감소 효과가 제한된다.
- **큰 배치** — RTT와 시스템 콜 비용을 크게 줄일 수 있지만 네트워크와 버퍼 부담이 커진다.
- **권장 방식** — 데이터 크기와 운영 환경에 맞게 테스트한 뒤 배치 크기를 정한다.

#### 파이프라이닝과 원자성

파이프라이닝은 트랜잭션이 아니다. 하나의 파이프라인에 여러 명령을 넣더라도 파이프라인 전체의 원자성을 보장하지 않는다.

여러 클라이언트가 동시에 Redis에 접근하는 상황에서는 한 클라이언트의 파이프라인 내부 명령 사이에 다른 클라이언트의 명령이 처리될 수 있다. 각 Redis 커맨드는 원자적으로 수행되지만, 파이프라인 전체가 하나의 원자적 단위가 되는 것은 아니다.

파이프라인 내부의 일부 커맨드에서 오류가 발생해도 전체 명령이 롤백되지 않는다. 오류가 발생한 커맨드만 실패하고, 나머지 커맨드는 정상적으로 수행된다.

| 구분 | 파이프라이닝 | 트랜잭션 |
|---|---|---|
| 목적 | 네트워크 왕복과 시스템 콜 감소 | 명령 묶음의 원자적 실행 |
| 원자성 | 보장하지 않음 | 보장함 |
| 오류 처리 | 일부 커맨드 실패 가능 | 트랜잭션 규칙에 따라 처리됨 |
| 성능 효과 | RTT 감소 효과가 큼 | 원자성 보장이 핵심임 |

### 클라이언트 사이드 캐싱

#### 클라이언트 사이드 캐싱 개념

클라이언트 사이드 캐싱은 Redis에서 조회한 데이터를 클라이언트 애플리케이션의 로컬 메모리에 저장해 재사용하는 방식이다. 애플리케이션이 자주 요청하는 데이터를 매번 Redis에 질의하지 않고 로컬 캐시에서 반환하면 네트워크 왕복 시간이 줄어든다.

예를 들어 애플리케이션이 `GET user:1234`를 실행해 `Alice`를 받으면, 이후 같은 값을 로컬 캐시에 저장해 재사용할 수 있다. 이 방식은 Redis 접근 횟수를 줄이고 응답 시간을 단축한다.

- **조회 비용 감소** — Redis에 매번 접근하지 않아도 되므로 네트워크 비용이 줄어든다.
- **서버 부하 감소** — Redis 서버가 처리해야 할 읽기 요청 수가 줄어든다.
- **적합한 데이터** — 자주 조회되지만 드물게 변경되는 데이터에 적합하다.

#### 데이터 정합성과 트래킹

클라이언트 사이드 캐싱은 데이터 정합성 문제가 있다. Redis에 저장된 값이 변경되면, 클라이언트의 로컬 캐시는 더 이상 최신 값이 아닐 수 있다. Redis는 이 문제를 처리하기 위해 클라이언트 트래킹 기능을 제공한다.

트래킹은 Redis 서버가 클라이언트가 캐시할 가능성이 있는 키를 기억하거나 prefix 단위 변경을 감지해 무효화 메시지를 보내는 기능이다. 클라이언트는 무효화 메시지를 받으면 해당 로컬 캐시를 삭제하거나 다시 조회한다.

#### Default Mode

Default Mode에서는 Redis 서버가 클라이언트가 접근한 키를 기억한다. 이후 동일한 키가 수정되면 Redis는 해당 키를 가지고 있을 가능성이 있는 클라이언트에게 무효화 메시지를 보낸다.

- **장점** — 클라이언트가 실제로 접근한 키에 대해서만 무효화 메시지를 보낸다.
- **단점** — Redis 서버가 클라이언트별 키 접근 정보를 기억해야 하므로 메모리 비용이 든다.
- **사용 대상** — 키 접근 범위가 넓지만 실제 캐시 키를 정확히 추적해야 하는 경우에 적합하다.

#### Broadcasting Mode

Broadcasting Mode에서는 Redis 서버가 클라이언트별 키 접근 내역을 저장하지 않는다. 대신 클라이언트가 관심 있는 prefix를 등록하고, 해당 prefix와 일치하는 키가 변경될 때 Redis가 무효화 메시지를 보낸다.

- **장점** — Redis 서버가 모든 키 접근을 기억하지 않으므로 메모리 부담이 작다.
- **단점** — 클라이언트가 실제로 캐시하지 않은 키 변경에 대해서도 무효화 메시지를 받을 수 있다.
- **비용** — prefix와 일치하는 키가 자주 변경되면 Redis 서버가 더 많은 무효화 메시지를 처리해야 하므로 CPU 자원을 사용할 수 있다.

#### 캐싱 모드 선택 기준

클라이언트 사이드 캐싱은 서비스 특성에 맞춰 선택해야 한다. 자주 조회되지만 드물게 변경되는 키는 캐싱 효율이 높다. 반대로 자주 변경되는 키나 넓은 prefix에 많은 변경이 발생하는 데이터는 무효화 메시지 비용이 커질 수 있다.

| 기준 | 적합한 선택 |
|---|---|
| 자주 조회되고 드물게 변경되는 키 | 클라이언트 사이드 캐싱 적용 |
| 클라이언트가 실제 접근한 키만 추적해야 하는 경우 | Default Mode |
| prefix 단위로 캐시 영역을 관리할 수 있는 경우 | Broadcasting Mode |
| prefix 변경이 매우 잦은 경우 | 캐싱 적용 신중 검토 |

클라이언트 사이드 캐싱은 빠른 캐시를 사용하면서도 데이터 정합성을 유지하기 위한 기능이다. 하지만 무효화 메시지, 서버 메모리, CPU 사용량을 함께 고려해야 한다.
