## 레디스 운영하기

### 레디스 모니터링 구축

레디스를 안정적으로 운영하려면 서버의 상태와 성능을 지속적으로 모니터링해야 한다. 대표적인 구성은 익스포터(Exporter), 프로메테우스(Prometheus), 그라파나(Grafana), 얼럿 매니저(Alertmanager)를 조합하는 방식이다.

- **익스포터** — 레디스 서버와 호스트의 메트릭을 프로메테우스가 읽을 수 있는 형식으로 노출한다. 레디스 메트릭은 redis_exporter가, 호스트 메트릭은 node_exporter가 담당한다.
- **프로메테우스** — 익스포터가 노출한 메트릭을 일정 주기로 수집(pull)해 시계열로 저장한다. alerting rule에 설정한 임계치를 넘으면 얼럿 매니저로 알람을 전달한다.
- **그라파나** — 프로메테우스에 저장된 데이터를 데이터 소스로 연결해 대시보드로 시각화한다.
- **얼럿 매니저** — 프로메테우스가 전달한 알람을 Slack, 디스코드 같은 채널로 발송한다.

프로메테우스를 거치지 않고 그라파나에서 레디스 데이터를 직접 확인하는 방법도 있다. 그라파나에 레디스 플러그인을 설치하면 익스포터 없이도 레디스 인스턴스에 직접 연결해 실시간 상태와 redis-cli 패널을 사용할 수 있다. 하지만 이 방식은 데이터를 시계열로 보관하지 않아 과거 시점의 그래프를 확인하기는 어렵다.

### 레디스 버전 업그레이드

레디스는 릴리스 주기가 빠르고 EOL(End Of Life)도 짧은 편이다. 버그와 보안 취약점에 대응하기 위해 최소한 EOL되지 않은 버전을 유지하도록 주기적으로 업그레이드하는 것이 좋다.

운영 중인 레디스를 업그레이드하는 방식은 크게 두 가지다.

| 방식            | 내용                                                | 특징                                                               |
| --------------- | --------------------------------------------------- | ------------------------------------------------------------------ |
| 새 서버에 복제  | 새 버전을 별도 서버에 설치하고 기존 데이터를 복제   | 애플리케이션의 접속 정보를 변경해야 하지만 다운타임이 없다         |
| 인스턴스 재실행 | 실행 중인 인스턴스를 중지하고 새 버전 소스로 재실행 | 접속 정보를 바꾸지 않아도 되지만 싱글 구성이면 다운타임이 발생한다 |

센티널이나 클러스터 같은 고가용성 구성이라면 복제본부터 하나씩 업그레이드해 다운타임 없이 전체 버전을 올릴 수 있다. 하지만 싱글 구성이거나 센티널이 없는 복제 구성이라면 다운타임이 발생하거나 접속 정보를 변경해야 하므로 상황에 맞는 방식을 선택해야 한다.

#### 센티널 구성의 무중단 업그레이드 원리

센티널 인스턴스를 먼저 새 버전으로 교체하고, 복제본을 새 버전으로 올린 뒤, 센티널에서 수동 페일오버를 수행해 새 버전 복제본을 마스터로 승격한다. 이후 구 버전이 된 기존 마스터를 같은 방식으로 올리고, 필요하면 페일오버를 한 번 더 수행해 원래 마스터로 되돌린다(페일백).

이 과정에서 복제본 인스턴스를 중지하기 전에 `config rewrite`를 수행해 런타임에 변경된 설정을 설정 파일에 반영해야 한다. 그렇지 않으면 재실행 시 변경된 설정이 유실된다.

#### 클러스터 구성의 무중단 업그레이드 원리

클러스터는 센티널 인스턴스를 고려할 필요가 없어 더 단순하다. 복제본 노드를 먼저 모두 업그레이드한 뒤, 각 마스터에 대해 페일오버로 복제본을 마스터로 승격하고, 구 버전이 된 기존 마스터를 다시 업그레이드하는 순서로 진행한다.

> **참고:** 현재 실행 중인 레디스 버전은 `INFO server` 커맨드의 `redis_version` 항목으로 확인할 수 있다.

### 장애 또는 성능 저하를 유발할 수 있는 레디스의 설정 항목

#### maxmemory-policy

`maxmemory-policy`는 레디스가 메모리 한계에 도달했을 때 어떤 키를 제거할지 결정하는 설정값이다. 기본값은 `noeviction`이며, 이 정책에서는 메모리가 가득 차도 데이터를 임의로 삭제하지 않고 더 이상 저장할 수 없다는 에러를 반환한다.

데이터 유실은 방지되지만 새로운 입력을 받지 못해 로직에 따라 애플리케이션 장애로 이어질 수 있다. 일부 데이터가 삭제되더라도 계속 입력을 받아들여야 한다면 `allkeys-lru`로 설정하는 것이 좋다.

#### stop-writes-on-bgsave-error

RDB 스냅숏이 정상적으로 저장되지 않았을 때 레디스로의 모든 쓰기 작업을 중지하는 설정이다. 백업 실패를 즉시 인지해 더 큰 장애를 방지할 수 있다. 기본값은 `yes`다.

하지만 이미 다른 모니터링으로 디스크 문제를 빠르게 감지할 수 있고 쓰기 작업이 중단되지 않기를 원한다면 이 값을 `no`로 변경한다. 그러면 백업 파일 생성에 실패해도 쓰기 작업이 계속 수행된다.

#### 자동 백업 옵션

RDB와 AOF로 백업 파일을 생성하는 작업은 운영 중인 인스턴스에 큰 부하를 줄 수 있다. 백업이 포그라운드(메인 스레드)에서 실행되면 그동안 다른 작업이 대기하고, 백그라운드에서 실행되면 COW(Copy-On-Write) 방식으로 동작해 메모리 사용량이 최대 maxmemory의 두 배까지 증가할 수 있다. maxmemory를 적절히 설정하지 않으면 최악의 경우 OOM 오류로 이어진다. 따라서 백업은 의도한 시간에 의도한 인스턴스에서 실행되도록 설정하는 것이 좋다.

`save`는 일정 기간 동안 변경된 키 개수가 조건을 만족하면 자동으로 RDB 파일을 생성한다. 기본값은 다음과 같다.

```
> CONFIG GET save
1) "save"
2) "3600 1 300 100 60 10000"
```

1시간(3600초) 동안 1번 이상, 5분(300초) 동안 100번 이상, 1분(60초) 동안 10,000번 이상 변경되면 RDB 파일을 생성한다는 의미다. 대규모 트래픽 환경에서는 백업 빈도가 너무 높아질 수 있으므로 기본값 대신 운영자가 원하는 시점에 백업이 수행되도록 설정하는 것이 좋다. 자동 RDB 생성을 끄려면 빈 문자열을 설정한다.

```
> CONFIG SET save ""
OK
```

`appendonly`를 `yes`로 설정해 AOF 백업을 사용하는 경우에도 주의가 필요하다. 기본적으로 AOF 파일 크기가 기존보다 100% 증가하면 자동 재작성이 발생한다.

```
> CONFIG GET auto-aof-*
1) "auto-aof-rewrite-percentage"
2) "100"
3) "auto-aof-rewrite-min-size"
4) "67108864"
```

자동 재작성을 원하지 않으면 `auto-aof-rewrite-percentage`를 0으로 변경해 운영자가 원하는 시점에 수동으로 재작성하도록 설정한다.

```
> CONFIG SET auto-aof-rewrite-percentage 0
OK
```

### 오래 걸리는 커맨드

레디스는 싱글 스레드로 동작하며 모든 요청은 이벤트 루프를 통해 순차적으로 실행된다. 한 번에 하나의 커맨드만 처리하므로 특정 커맨드의 실행 시간이 길어지면 다른 모든 클라이언트가 대기하게 된다. 따라서 O(N) 이상의 시간 복잡도를 갖는 커맨드는 지양해야 한다.

KEYS나 FLUSHALL처럼 여러 키에 한 번에 접근하는 커맨드만 오래 걸린다고 생각하기 쉽다. 하지만 set, list, hash처럼 하나의 자료 구조에 여러 아이템이 들어 있으면 해당 자료 구조에 대한 커맨드도 아이템 개수에 비례해 실행 시간이 늘어난다.

**키스페이스 커맨드** — N은 레디스에 저장된 전체 키의 개수를 의미한다.

| 커맨드   | 시간 복잡도 | 설명                                                                                  |
| -------- | ----------- | ------------------------------------------------------------------------------------- |
| KEYS     | O(N)        | 모든 키에 접근한다. 키가 많으면 SCAN으로 대체하는 것이 좋다                           |
| FLUSHALL | O(N)        | 모든 키를 삭제한다. 옵션 없이 쓰면 SYNC로 동작해 완료까지 다른 응답을 처리하지 못한다 |
| FLUSHDB  | O(N)        | 선택된 데이터베이스의 모든 키를 삭제한다. 동작 방식은 FLUSHALL과 같다                 |

FLUSHALL과 FLUSHDB는 ASYNC 옵션과 함께 쓰면 삭제 작업이 백그라운드에서 수행돼 다른 작업을 블락하지 않는다. 이때 삭제 실행 중에 새로 생성된 키는 삭제되지 않는다.

> **참고: LAZY FREEING**
> 레디스는 기본적으로 DEL 커맨드로 키를 동기 삭제한다. string이나 아이템이 적은 자료 구조는 빠르게 삭제되지만, 수백만 개의 아이템을 가진 큰 키는 삭제에 시간이 오래 걸린다. 이런 경우 비동기로 메모리를 해제하는 UNLINK를 사용할 수 있다.
>
> 키 삭제는 사용자가 직접 DEL을 호출할 때뿐 아니라 maxmemory 도달로 인한 이빅션, 키 만료, RENAME 같은 커맨드의 사이드이펙트, 복제 동기화 시 데이터 전체 삭제(FLUSH) 등 시스템 내부에서도 발생한다.
>
> 이러한 삭제를 비동기로 처리하도록 `lazyfree-lazy-eviction`, `lazyfree-lazy-expire`, `lazyfree-lazy-server-del`, `replica-lazy-flush`, `lazyfree-lazy-user-del` 설정을 `yes`로 변경할 수 있다. 기본값은 모두 `no`다. 이 설정을 켜면 키와 값의 연결은 즉시 해제되지만 데이터가 메모리에서 바로 사라지지 않고 일시적으로 남아 메모리 사용량이 예상보다 늘어날 수 있으므로 모니터링이 필요하다.
>
> lazyfree를 `yes`로 지정해도 항상 비동기로 삭제되는 것은 아니다. 레디스는 `lazyfreeGetFreeEffort`로 키 해제에 드는 노력을 계산해, 그 값이 `LAZYFREE_THRESHOLD`(64)보다 크고 객체의 참조 카운트가 1일 때만 비동기로 해제한다. 노력이 64 이하이거나 객체가 공유되고 있으면 동기적으로 DEL을 사용한다.

자료 구조별로 O(N) 이상의 시간 복잡도를 갖는 주요 커맨드는 다음과 같다.

**자료 구조 공통**

| 커맨드  | 시간 복잡도    | 설명                                                                                                              |
| ------- | -------------- | ----------------------------------------------------------------------------------------------------------------- |
| DEL     | O(1) ~ O(N)    | string은 O(1), list·set·sorted set·hash는 아이템 개수에 비례한다. 포그라운드 삭제이므로 큰 키는 UNLINK를 권장한다 |
| SORT    | O(N + Mlog(M)) | list·set·sorted set의 아이템을 정렬해 반환한다. N은 내부 아이템 수, M은 반환 아이템 수다                          |
| SORT_RO | O(N + Mlog(M)) | 레디스 7에서 추가됐다. STORE 옵션이 없는 읽기 전용이라 복제본에서도 수행할 수 있다                                |

**set 관련 커맨드** — 집합 연산은 집합의 카디널리티에 비례해 수행 시간이 늘어난다.

| 커맨드                            | 시간 복잡도 | 설명                                                                                                                               |
| --------------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| SDIFF / SDIFFSTORE                | O(N)        | 차집합. N은 연산에 참여하는 집합의 아이템 총 개수다                                                                                |
| SUNION / SUNIONSTORE              | O(N)        | 합집합. N은 연산에 참여하는 집합의 아이템 총 개수다                                                                                |
| SINTER / SINTERSTORE / SINTERCARD | O(N\*M)     | 교집합. N은 가장 작은 집합의 카디널리티, M은 집합의 수다. SINTERCARD(레디스 7)는 카디널리티만 반환하며 LIMIT로 조기 종료할 수 있다 |

**list 관련 커맨드** — 양 끝을 제외한 특정 인덱스 접근은 아이템 수에 비례하므로 최악의 경우 전체를 순회한다.

| 커맨드  | 시간 복잡도 | 설명                                                                    |
| ------- | ----------- | ----------------------------------------------------------------------- |
| LINDEX  | O(N)        | 인덱스 위치의 아이템을 반환한다. N은 해당 위치까지 지나치는 아이템 수다 |
| LINSERT | O(N)        | 피봇 값 앞뒤에 삽입한다. N은 피봇까지 지나치는 아이템 수다              |
| LSET    | O(N)        | 특정 인덱스의 아이템을 변경한다. N은 list 길이다                        |
| LPOS    | O(N)        | 레디스 6.0.6에서 추가됐다. 문자열의 인덱스를 반환한다. N은 list 길이다  |

**hash 관련 커맨드**

| 커맨드  | 시간 복잡도 | 설명                           |
| ------- | ----------- | ------------------------------ |
| HGETALL | O(N)        | 모든 필드의 키와 값을 반환한다 |
| HKEYS   | O(N)        | 모든 필드의 키를 반환한다      |
| HVALS   | O(N)        | 모든 필드의 값을 반환한다      |

**sorted set 관련 커맨드** — 데이터가 입력될 때 자동 정렬되므로 기본적으로 O(log(N))으로 효율적이다. 하지만 집합 연산은 set과 마찬가지로 아이템 개수에 비례해 시간이 늘어난다.

| 커맨드                            | 시간 복잡도          | 설명                                                                                                                      |
| --------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| ZDIFF / ZDIFFSTORE                | O(L+(N-K)log(N))     | 차집합. L은 전체 아이템 수, N은 첫 집합 크기, K는 결과 크기다                                                             |
| ZUNION / ZUNIONSTORE              | O(N)+O(M\*log(M))    | 합집합. N은 전체 아이템 수, M은 결과 아이템 수다                                                                          |
| ZINTER / ZINTERSTORE / ZINTERCARD | O(N\*K)+O(M\*log(M)) | 교집합. N은 가장 작은 집합의 카디널리티, K는 집합 수, M은 결과 카디널리티다. ZINTERCARD(레디스 7)는 카디널리티만 반환한다 |

### 트랜잭션과 루아 스크립트

레디스는 원자적으로 수행돼야 하는 커맨드를 보장하기 위해 두 가지 방식의 트랜잭션을 제공한다. 싱글 스레드로 동작하는 만큼 사용 시 주의가 필요하다.

**MULTI / EXEC** — MULTI로 트랜잭션을 시작하고 실행할 커맨드를 입력하면 즉시 실행되지 않고 큐에 쌓인다(QUEUED). 이후 EXEC를 호출하면 큐에 쌓인 커맨드가 순차적으로 한 번에 실행된다.

```
> MULTI
OK
(TX)> INCRBY account_balance 100
QUEUED
(TX)> RPUSH transaction_log "입금 100"
QUEUED
(TX)> EXEC
1) (integer) 100
2) (integer) 1
```

**루아 스크립트** — 여러 커맨드를 하나의 스크립트로 묶어 레디스 서버 내에서 실행한다. SCRIPT LOAD로 스크립트를 등록하면 hash 값을 반환하고, 이후 EVALSHA로 본문을 다시 전송하지 않고 캐싱된 스크립트를 실행할 수 있다.

```lua
local key = KEYS[1]
local amount = tonumber(ARGV[1])

local newBalance = redis.call('INCRBY', key, amount)

local logMessage = '입금 ' .. amount
local logCount = redis.call('RPUSH', 'transaction_log', logMessage)

return { newBalance, logCount }
```

트랜잭션과 루아 스크립트를 이용하면 여러 키에 대한 작업을 원자적으로 실행해 데이터 일관성을 유지할 수 있다. 하지만 트랜잭션이나 스크립트 내부에서 BLPOP, BRPOP 같은 블로킹 커맨드를 사용하면 안 된다. 다른 키를 기다리며 전체가 멈출 수 있어, 레디스는 이 경우 트랜잭션을 취소(EXECABORT)하거나 스크립트 실행을 거부한다.

### has-get / has-del 패턴

데이터를 조회하거나 삭제하기 전에 EXISTS로 존재 여부를 먼저 확인하는 has-get / has-del 패턴은 지양하는 것이 좋다. 존재 확인을 위한 커맨드가 추가되면서 네트워크 왕복과 레디스 호출이 늘어나기 때문이다.

10만 개의 키를 대상으로 has-get 패턴(EXISTS 후 GET)과 직접 GET을 비교하면 같은 작업에서 전자가 약 두 배의 시간이 걸린다(예시 측정에서 223.43초 대 110.71초).

레디스에서 GET 같은 조회 커맨드는 키가 없으면 nil을 반환하고, DEL은 키가 없어도 에러 없이 동작한다. 따라서 존재 여부를 먼저 확인할 필요 없이 바로 조회·삭제하는 것이 효율적이다. 대규모 트래픽 환경에서는 이런 차이가 누적돼 비용과 사용자 경험에 영향을 준다.

### 클라이언트 출력 버퍼 사이즈

클라이언트 출력 버퍼(client output buffer)는 클라이언트가 서버 응답을 받을 때 이를 일시적으로 저장하는 공간이다. 통신 속도 차이나 부하로 발생할 수 있는 버퍼 오버플로우를 방지한다. `redis.conf`에서 클래스별로 하드 제한, 소프트 제한, 소프트 초를 설정한다.

```
client-output-buffer-limit normal 0 0 0
client-output-buffer-limit replica 256mb 64mb 60
client-output-buffer-limit pubsub 32mb 8mb 60
```

| 클래스  | 하드 제한 | 소프트 제한 | 동작                                                         |
| ------- | --------- | ----------- | ------------------------------------------------------------ |
| normal  | 0         | 0           | 제한 비활성화. 일반 클라이언트는 제한 없이 데이터를 수신한다 |
| replica | 256MB     | 64MB        | 소프트 제한을 60초 동안 계속 초과하면 연결을 종료한다        |
| pubsub  | 32MB      | 8MB         | 소프트 제한을 60초 동안 계속 초과하면 연결을 종료한다        |

maxmemory를 늘리거나 maxclients를 확장할 때는 복제본 출력 버퍼 크기도 함께 조절하는 것이 중요하다. 그렇지 않으면 큰 데이터를 복제할 때 복제 버퍼가 가득 차 부분 동기화(partial sync)나 데이터 손실로 이어질 수 있다.

### 키스페이스 알림을 사용한 키 만료 모니터링

키스페이스 알림(keyspace notification)은 레디스 내부 키의 변경 사항을 내부 pub/sub 채널로 구독할 수 있는 기능이다. 키 만료를 감시하다가 만료 이벤트가 발생하면 애플리케이션에서 필요한 작업을 수행할 수 있다.

`notify-keyspace-events` 설정에 수신할 이벤트를 문자 조합으로 지정한다.

| 문자                  | 의미                                                              |
| --------------------- | ----------------------------------------------------------------- |
| K                     | 키스페이스 이벤트. `__keyspace@<db>__` 접두사로 발행              |
| E                     | 키 이벤트. `__keyevent@<db>__` 접두사로 발행                      |
| g                     | DEL, EXPIRE, RENAME 같은 일반 명령 이벤트                         |
| $ / l / s / h / z / t | 각각 string / list / set / hash / sorted set / stream 명령 이벤트 |
| x                     | 만료된 키 이벤트                                                  |
| e                     | 이빅션으로 삭제된 키 이벤트                                       |
| m                     | 존재하지 않는 키에 접근한 key-miss 이벤트                         |
| n                     | 새로운 키 이벤트                                                  |
| A                     | m과 n을 제외한 모든 이벤트를 포함하는 별칭                        |

키 이벤트(E)와 만료 이벤트(x)를 받으려면 다음과 같이 설정한다.

```
> CONFIG SET notify-keyspace-events Ex
OK
```

이후 `__keyevent@0__:expired` 채널을 구독하면 키가 만료될 때 메시지를 수신한다.

```
> SUBSCRIBE __keyevent@0__:expired
1) "message"
2) "__keyevent@0__:expired"
3) "my_key"
```

하지만 많은 키가 동시에 만료되면 그만큼 많은 이벤트 메시지가 한꺼번에 발생한다. pub/sub 버퍼 크기를 초과하면 새 메시지가 버퍼에 저장되지 못하고 유실될 수 있다. pub/sub은 fire and forget 방식이라 한 번 발행된 이벤트는 재확인할 수 없고, 클라이언트 연결이 끊긴 동안 전달된 이벤트도 놓친다. 따라서 키 만료를 안정적으로 감지해야 하는 서비스라면 pub/sub 버퍼 크기를 늘리거나 여러 인스턴스로 이벤트를 분산 처리하는 방법을 고려해야 한다.

### 특정 프리픽스를 가진 키 삭제하기

레디스는 특정 프리픽스로 키를 한 번에 삭제하는 기능을 제공하지 않는다. 따라서 SCAN으로 해당 프리픽스의 키를 찾아 하나씩 삭제해야 한다.

```python
pattern = 'prefix:*'
cursor, keys = 0, []

# SCAN으로 특정 프리픽스를 가진 키 검색
while True:
    cursor, partial_keys = r.scan(cursor, match=pattern)
    keys.extend(partial_keys)
    if cursor == 0:
        break

# 검색된 키 삭제
for key in keys:
    r.delete(key)
```

이 방식은 키를 찾는 SCAN 왕복과 키를 지우는 DEL 왕복이 각각 반복된다. 레디스에 1000만 개의 키가 있고 매치하는 키가 100만 개라면 SCAN 이후 100만 번의 DEL 왕복이 추가로 필요해 시간이 오래 걸린다.

루아 스크립트를 이용하면 SCAN과 DEL을 서버 내부에서 처리해 네트워크 I/O를 줄일 수 있다. DEL 왕복이 사라지고 커서를 받아오는 횟수만큼만 왕복이 발생한다.

```python
pattern = 'prefix:*'
count = 100
cursor = "0"

lua_script = """
local cursor = ARGV[1]
local pattern = ARGV[2]
local count = ARGV[3]

local keys = redis.call("SCAN", cursor, "MATCH", pattern, "COUNT", count)
local cursor = keys[1]
local keyList = keys[2]

for _, key in ipairs(keyList) do
    redis.call("DEL", key)
end

return {cursor, #keyList}
"""

total_deleted_count = 0

while True:
    result = r.eval(lua_script, 0, cursor, pattern, count)
    cursor, deleted_count = result[0], result[1]
    total_deleted_count += deleted_count

    if cursor == "0":
        break
```

하지만 루아 스크립트는 실행되는 동안 다른 클라이언트의 커맨드를 차단한다. 운영 환경에서 삭제할 때는 다른 클라이언트에 영향을 주지 않도록 `count` 매개변수로 한 번에 처리할 배치 크기를 조절해 차단 시간을 최소화해야 한다.

> **주의:** 삭제 작업은 마스터 인스턴스에서만 수행할 수 있으므로 운영 중인 서비스에 영향을 주지 않도록 주의 깊게 실행해야 한다.

### 레디스 모니터링 지표

#### 슬로우 로그

슬로우 로그(Slow Log)는 실행 속도가 느린 커맨드를 기록하는 로그다. 주기적으로 모니터링해 느린 커맨드를 추적하고 디버깅하면 성능을 개선할 수 있다. `SLOWLOG GET`으로 확인한다.

```
> SLOWLOG GET
 1) 1) (integer) 1923
    2) (integer) 1696344048
    3) (integer) 35233
    4) 1) "SCAN"
       2) "10179327"
       3) "COUNT"
       4) "50000"
```

각 레코드는 고유 ID, 실행 시각(Timestamp), 실행에 소요된 시간(마이크로초), 느리게 수행된 커맨드와 인자를 나타낸다.

기록 기준은 `slowlog-log-slower-than`으로 변경한다. 단위는 마이크로초(μs)이며 기본값은 10000μs, 즉 10밀리초다. 이 값보다 오래 걸린 커맨드가 슬로우 로그에 기록된다. `slowlog-max-len`은 유지되는 레코드 개수를 제한하며 기본값은 128개다. 최대 개수를 넘으면 오래된 레코드가 새 레코드로 대체된다.

슬로우 로그가 평소보다 크게 늘어나면 성능 문제가 발생했을 가능성을 의심하고 확인하는 것이 좋다. 예상치 못한 커맨드나 악의적인 커맨드를 식별하는 데에도 도움이 된다.

#### 그래프 지표

CPU, 메모리, 네트워크 같은 자원을 적절히 모니터링해야 한다. 과다 사용은 높은 지연 시간과 성능 저하를, 과소 사용은 요구 사항에 맞지 않는 과도한 리소스 사용을 의미한다.

**CPU** — 레디스는 커맨드 실행 중에는 싱글 스레드로 동작하지만 백업이나 UNLINK 같은 백그라운드 작업에서는 다른 CPU를 활용한다. 시간 복잡도가 높은 커맨드를 자주 사용하거나, 집합의 카디널리티가 높거나, 단일 hash에 항목이 너무 많으면 CPU 부하가 늘어난다. CPU 부하가 높을 때 읽기 작업이 원인이라면 읽기를 복제본으로 분산하고, 백업도 가능하면 복제본에서 수행하는 것이 좋다.

**메모리** — 핵심 지표는 `used_memory`로, 레디스가 논리적으로 할당한 메모리를 나타낸다. 메모리 사용률이 100%에 도달하면 maxmemory 정책에 따라 이빅션이 발생할 수 있다. 캐시 용도로는 의도적인 동작일 수 있지만 데이터 삭제를 원치 않는다면 이빅션의 발생량을 모니터링해야 한다. 과도한 이빅션은 CPU 사용량 증가로도 이어진다.

`used_memory`가 논리적 사용량이라면 `used_memory_rss`는 운영체제가 레디스 프로세스에 할당한 실제 물리 메모리를 반영한다. 물리 메모리가 논리 메모리보다 지나치게 커지면 메모리 단편화(fragmentation)가 의심된다. 키가 한꺼번에 몰렸다 삭제되거나 만료로 이빅션이 대량 발생할 때 자주 나타난다. 단편화가 심하면 active defragmentation 기능을 활성화할 수 있다. 레디스 4.0 이상에서 사용 가능하며 기본값은 비활성화다.

```
CONFIG SET activedefrag yes
```

**네트워크** — 네트워크 I/O 지표로 트래픽이 예상치를 초과하지 않는지 확인한다. VM, 도커, 쿠버네티스 환경에서는 노드의 네트워크 대역폭 한계에 도달하면 레디스가 더 많은 명령을 처리할 수 있어도 낮은 처리량을 내는 병목이 생긴다. 네트워크 사용량이 읽기 작업 때문이면 복제본으로 읽기를 분산하고, 쓰기 작업 때문이면 서버 사양을 올리거나 클러스터 모드로 쓰기를 여러 노드에 분산한다.

**커넥션** — 활성 연결 수와 신규 연결 수의 변화를 주시한다. 활성 연결이 갑자기 늘면 연결이 올바르게 종료되지 않고 남아 있는지 확인해야 한다. `tcp-keepalive`를 활용하면 유휴 연결로 인한 문제를 예방할 수 있고, 기본 설정에서는 매 300초마다 연결 유효성을 확인한다. 새로운 연결 설정에는 비용이 크므로 커넥션 풀링으로 기존 연결을 재사용하는 것이 좋다. TLS를 사용하는 경우 핸드셰이크에 더 많은 시간과 CPU가 들어가므로 신규 연결의 양을 제어해야 한다.

**복제** — 마스터는 복제본이 있으면 지속적으로 데이터 명령 스트림을 전송한다. 복제 지연이 급증하면 복제본이 마스터의 속도를 따라가지 못한다는 의미다. 복제 지연이 길어지면 복제본이 전체 동기화를 요청할 수 있고, 이때 마스터에서 스냅숏을 생성하므로 성능 저하가 발생한다. 마스터로의 과도한 쓰기, 네트워크 대역폭 고갈, 복제 출력 버퍼 크기 문제 등이 원인이 될 수 있으므로 관련 지표를 함께 확인하는 것이 좋다.
