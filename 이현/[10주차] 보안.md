# 11장. 보안

## 커넥션 제어

레디스에 누가 접속할 수 있는지 제어하는 방법이다.

### bind

Redis 서버가 어떤 네트워크 인터페이스(IP)에서 들어오는 연결을 허용할지 지정한다.

예시

- `bind 127.0.0.1` : 로컬 서버만 접근 가능
- `bind 10.0.0.20` : 특정 내부망 서버만 접근 가능
- `bind 0.0.0.0` : 모든 IP 접근 가능

### 🤔 bind가 잘 이해 안 간다

예를 들어

```
웹 서버 : 10.0.0.10
Redis : 10.0.0.20
```

이라면 Redis는 웹 서버만 접근하면 된다.

하지만 `bind 0.0.0.0` 으로 설정하면 인터넷 어디서든 Redis에 접속을 시도할 수 있다.

반면 `bind 10.0.0.20` 으로 설정하면 내부망 서버만 접근 가능하다.

즉 bind는

> 어떤 서버가 Redis에 연결할 수 있는가
> 

를 결정하는 설정이다.

---

### 패스워드

접속한 사용자가 Redis를 사용할 수 있는지 인증하는 기능이다.

Redis 6 이전에는 `requirepass password` 를 사용했다.

접속 시에는 `AUTH password` 또는 `redis-cli -a password` 로 인증한다.

### 한계

- 사용자 구분 불가
- 권한 구분 불가
- 비밀번호 하나 유출 시 전체 접근 가능

현재는 ACL 사용이 권장된다.

---

### Protected Mode

Redis 3.2부터 추가된 보안 기능

기본값은 `protected-mode yes`

운영 환경에서도 사용을 권장한다.

### 동작 방식

다음 조건을 모두 만족하면

- `protected-mode yes`
- bind 설정 없음
- 패스워드 없음

Redis는 외부 연결을 거부한다.

오직 localhost 에서만 접속 가능하다.

### 🤔 왜 필요할까?

운영자가 실수로

- `bind 0.0.0.0`
- 패스워드 없음

상태로 Redis를 실행했을 수 있다.

이 경우 누구나 Redis에 접근할 수 있다.

Protected Mode는 이런 위험한 상황을 자동으로 막아주는 안전장치 역할을 한다.

---

## 커맨드 제어

Redis에는 서버 설정을 변경하거나 서버 동작을 제어하는 위험한 명령어가 존재한다.

대표적으로

- `CONFIG`
- `DEBUG`
- `MODULE`

등이 있다.

운영자가 커맨드라인으로 Redis를 편리하게 제어할 수 있다는 장점이 있지만, 접근 가능한 사용자가 Redis 설정을 변경할 수 있다는 점에서는 위험할 수 있다.

예를 들어

- `CONFIG GET *`
- `CONFIG SET requirepass test`
- `CONFIG SET dir /tmp`

등의 명령을 실행할 수 있다.

---

### 커맨드 이름 변경

특정 명령어 이름을 변경할 수 있다.

예시

`rename-command CONFIG MY_CONFIG`

설정 이후에는

- `CONFIG GET *` → 실패
- `MY_CONFIG GET *` → 성공

### 🤔 이것도 잘 이해 안 감

ACL이 없던 시절에는 위험한 명령을 숨기기 위해 사용했다.

예를 들어

```
CONFIG → MY_CONFIG
FLUSHALL → ABCD_FLUSHALL
```

처럼 명령어 이름을 변경한다.

공격자는 원래 이름을 모르기 때문에 실행할 수 없다.

하지만 결국 이름만 바뀐 것이다.

```
CONFIG → MY_CONFIG
```

변경된 이름을 알게 되면 원래 CONFIG와 동일하게 사용할 수 있다.

즉

| 구분 | rename-command |
| --- | --- |
| 권한 차단 | ❌ |
| 이름 숨김 | ⭕ |

수준의 보안이다.

### Sentinel 사용 시 주의

Sentinel은 장애 발생 시 Redis에 직접 명령을 전송한다.

대표적으로

- `CONFIG`
- `REPLICAOF`

명령을 사용한다.

만약 Redis에서 커맨드 이름을 변경했다면 Sentinel도 변경된 이름을 알아야 한다.

따라서

- `redis.conf`
- `sentinel.conf`

를 동일하게 수정해야 한다.

그렇지 않으면 페일오버가 정상적으로 동작하지 않을 수 있다.

---

### 커맨드 실행 환경 제어

Redis 7부터는 위험한 명령어 실행 자체를 제한할 수 있다.

대표 옵션

- `enable-protected-configs no`
- `enable-debug-command no`
- `enable-module-command no`

### enable-protected-configs

위험한 CONFIG 명령 실행 제한

예시

- `CONFIG SET dir`
- `CONFIG SET dbfilename`

같은 설정 변경 차단

### enable-debug-command

DEBUG 명령 실행 제한

예시

- `DEBUG SLEEP`
- `DEBUG SEGFAULT`

같은 명령 차단

### enable-module-command

MODULE 명령 실행 제한

예시

- `MODULE LOAD evil.so`

같은 악성 모듈 로딩 차단

### 🤔 왜 이런 옵션이 생겼을까?

과거 Redis 해킹 사례 때문이다.

공격자가 Redis에 접근한 뒤

- `CONFIG SET dir`
- `CONFIG SET dbfilename`

를 이용해 파일 저장 위치를 변경하거나

`MODULE LOAD`

을 이용해 악성 모듈을 로딩할 수 있었다.

그래서 위험한 명령 자체를 차단하는 기능이 추가됐다.

---

### 레디스를 이용한 해킹 사례

보안이 취약한 Redis를 이용해 서버를 해킹할 수 있는 사례가 존재한다.

### 공격 흐름

```
공격자 → SSH 키 생성
→ Redis 접속
→ CONFIG SET dir /root/.ssh
→ CONFIG SET dbfilename authorized_keys
→ SAVE
→ SSH 접속 성공
```

### 왜 가능했을까?

Redis는 `CONFIG SET dir`, `CONFIG SET dbfilename` 를 이용해 저장 위치를 변경할 수 있기 때문이다.

공격자는 자신의 공개키를 Redis 데이터로 저장한 뒤 SSH 인증 파일로 만들 수 있었다.

또한 Redis는 기존 데이터를 삭제하고 새로운 데이터를 삽입할 수 있기 때문에 악용될 수 있다.

### 대응 방법

- `protected-mode yes`
- ACL 사용
- Redis 외부 노출 금지
- `enable-protected-configs no`

패스워드를 사용하지 않는다면 최소한 `enable-protected-configs local` 또는 `enable-protected-configs no` 로 설정해 외부에서 Redis 설정을 변경할 수 없도록 하는 것이 좋다.

## ACL

Access Control List

실행 가능한 커맨드와 접근 가능한 키를 유저별로 제한하는 기능이다.

Redis 6부터 지원한다.

기존에는 `rename-command` 를 이용해 위험한 명령어를 숨겼지만 이는 일시적인 보안에 불과했다.

변경된 이름이 노출되면 우회가 가능했기 때문이다.

ACL은 사용자별 권한 자체를 제어할 수 있다.

---

### 유저의 생성과 삭제

유저 생성

`ACL SETUSER app-user on >password`

유저 삭제

`ACL DELUSER app-user`

---

### 유저 상태 제어

활성화

`ACL SETUSER app-user on`

비활성화

`ACL SETUSER app-user off`

---

### 패스워드

패스워드 설정

`ACL SETUSER app-user >password`

하나의 유저에 여러 개의 패스워드를 설정할 수도 있다.

---

### 패스워드 저장 방식

Redis는 패스워드를 평문으로 저장하지 않는다.

내부적으로 해시값 형태로 저장한다.

따라서 ACL LIST 명령을 실행해도 실제 패스워드는 확인할 수 없다.

---

### 커맨드 권한 제어

ACL은 사용자별 실행 가능한 명령을 제한할 수 있다.

예시

| 설정 | 의미 |
| --- | --- |
| `+GET` | GET 허용 |
| `+SET` | SET 허용 |
| `-FLUSHALL` | FLUSHALL 금지 |
| `+@all` | 모든 명령 허용 |
| `-@dangerous` | 위험 명령 차단 |

예시

`ACL SETUSER app-user +GET +SET -FLUSHALL`

---

### 키 접근 제어

특정 키 패턴에 대해서만 접근을 허용할 수 있다.

예시

`ACL SETUSER app-user ~user:*`

허용

- `user:1`
- `user:100`
- `user:999`

차단

- `admin:1`
- `cache:1`

### 🤔 왜 필요할까?

하나의 Redis를 여러 서비스가 함께 사용할 수 있다.

예를 들어

```
user:* → 회원 서비스
order:* → 주문 서비스
```

라면 회원 서비스가 주문 데이터를 조회하지 못하도록 제한할 수 있다.

---

### 셀렉터

Redis 7에서 추가된 기능

하나의 사용자에 대해 여러 ACL 규칙 그룹을 설정할 수 있다.

예시

```
user:* → GET, SET

cache:* → GET
```

기존 ACL보다 복잡한 권한 구성이 가능하다.

---

### pub/sub 채널 접근 제어

Pub/Sub 채널 단위 접근 제어 가능

예시

`ACL SETUSER app-user &notice:*`

허용

- `notice:event`
- `notice:user`

차단

- `admin:event`

---

### 유저 초기화

ACL 규칙 전체 삭제

`ACL SETUSER app-user reset`

사용자에 부여된 권한, 패스워드, 키 접근 정책 등을 모두 제거한다.

---

### ACL 규칙 파일로 관리하기

ACL 정보를 별도 파일로 관리할 수 있다.

설정

`aclfile /etc/redis/users.acl`

### 장점

- 사용자 관리
- 버전 관리
- 백업
- 배포 자동화

### 🤔 ACL은 왜 등장했을까?

기존에는

`rename-command CONFIG MY_CONFIG`

처럼 위험한 명령어를 숨겼다.

하지만 변경된 이름이 노출되면 누구나 사용할 수 있었다.

ACL은

```
사용자 A → CONFIG 금지
사용자 B → CONFIG 허용
```

처럼 실제 권한 자체를 제어할 수 있다.

| 구분 | rename-command | ACL |
| --- | --- | --- |
| 방식 | 이름 변경 | 권한 제어 |
| 사용자별 제어 | 불가 | 가능 |
| 보안 수준 | 낮음 | 높음 |

## SSL/TLS

Redis 통신을 암호화하는 기능이다.

---

### SSL/TLS란?

기본 Redis 통신

`Client ⇄ Redis`

TLS 적용

`Client ⇄ TLS ⇄ Redis`

### 🤔 왜 필요할까?

패킷을 탈취하더라도

- 비밀번호
- 세션 정보
- 데이터

를 확인할 수 없다.

---

### 레디스에서 SSL/TLS 사용하기

대표 설정

- `tls-port 6379`
- `tls-cert-file server.crt`
- `tls-key-file server.key`
- `tls-ca-cert-file ca.crt`

접속

`redis-cli --tls`

---

### SSL/TLS를 사용한 HA 구성

복제 구성

`Master ⇄ TLS ⇄ Replica`

Sentinel 구성

`Sentinel ⇄ TLS ⇄ Redis`

Cluster 구성

`Master ⇄ TLS ⇄ Master`

모든 노드 간 통신을 TLS 기반으로 구성할 수 있다.
