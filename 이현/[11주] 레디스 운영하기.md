# 13.1 레디스 모니터링 구축하기

Redis는 메모리 기반 데이터베이스이기 때문에 장애가 발생하면 서비스 전체에 영향을 줄 수 있다. 따라서 CPU, 메모리, 네트워크, 복제 상태 등을 지속적으로 모니터링하여 이상 징후를 빠르게 발견하는 것이 중요하다.

---

## 프로메테우스와 그라파나를 이용한 레디스 모니터링

Redis를 모니터링할 때 가장 많이 사용하는 조합은 **Prometheus + Grafana**이다.

```
               Redis
                  │
          Redis Exporter
                  │
         Prometheus (수집)
                  │
        Grafana (시각화)
                  │
      Slack / Email 알림
```

각 구성 요소의 역할은 다음과 같다.

| 구성 요소 | 역할 |
| --- | --- |
| Redis Exporter | Redis 정보를 Prometheus가 읽을 수 있는 메트릭으로 변환 |
| Prometheus | 메트릭 수집 및 저장 |
| Grafana | 메트릭 시각화 및 Dashboard 제공 |
| AlertManager | 임계치 초과 시 알림 전송 |

### Redis Exporter

Redis는 Prometheus 형식의 메트릭을 제공하지 않는다.

따라서 Redis Exporter가 Redis의 정보를 읽어 다음과 같은 메트릭으로 변환한다.

```
redis_memory_used_bytes
redis_connected_clients
redis_commands_processed_total
redis_evicted_keys_total
```

Prometheus는 이 메트릭을 주기적으로 수집하여 저장한다.

### 🤔 왜 Exporter가 필요할까?

Prometheus는 애플리케이션이 제공하는 메트릭만 수집할 수 있다. Redis Exporter는 Redis의 `INFO` 명령을 이용해 다양한 정보를 읽고 Prometheus 형식으로 변환하는 역할을 수행한다.

---

### Prometheus

Prometheus는 오픈소스 모니터링 시스템으로, 일정 주기마다 Exporter에 HTTP 요청(Pull 방식)을 보내 메트릭을 수집한다.

주요 특징

- Pull 방식으로 데이터 수집
- 시계열(Time Series) 데이터 저장
- PromQL 지원
- Alert Rule 작성 가능

예를 들어 메모리 사용률은 다음과 같이 계산할 수 있다.

```
used_memory / maxmemory
```

---

### Grafana

Grafana는 Prometheus에 저장된 메트릭을 Dashboard 형태로 시각화한다.

대표적으로 다음과 같은 정보를 확인할 수 있다.

- Memory 사용량
- CPU 사용량
- Connected Clients
- Commands/sec
- Cache Hit Ratio
- Replication 상태

운영자는 Dashboard를 통해 Redis의 현재 상태를 한눈에 확인할 수 있다.

---

### AlertManager

Prometheus는 특정 조건을 만족하면 Alert를 발생시킬 수 있다.

예를 들어 다음과 같은 상황에서 알림을 보낼 수 있다.

- Memory 사용률 90% 초과
- Redis Down
- Replication Lag 증가
- Connected Client 급증

AlertManager는 Slack, Email, Teams 등 다양한 채널과 연동하여 운영자가 장애를 빠르게 인지할 수 있도록 도와준다.

---

## 레디스 플러그인을 이용한 그라파나 대시보드

Grafana에는 Redis 전용 Plugin이 제공된다.

Redis Plugin을 사용하면 Prometheus 없이도 Redis 정보를 직접 조회하여 Dashboard를 구성할 수 있다.

```
Grafana
    │
Redis Plugin
    │
Redis
```

### 장점

- 설치가 간단하다.
- Redis만 모니터링한다면 빠르게 Dashboard를 구성할 수 있다.
- 별도의 Prometheus 구축이 필요하지 않다.

### 단점

- 장기간 메트릭 저장이 어렵다.
- Alert 기능이 제한적이다.
- 여러 시스템을 함께 모니터링하기 어렵다.

### 🤔 운영 환경에서는 어떤 방식을 사용할까?

Redis만 간단하게 확인하는 목적이라면 Plugin만으로도 충분하다. 하지만 실제 운영 환경에서는 Redis뿐만 아니라 서버, 애플리케이션, 데이터베이스까지 함께 모니터링해야 하므로 **Prometheus + Grafana** 구성을 가장 많이 사용한다.

---

# 13.2 레디스 버전 업그레이드

Redis는 새로운 기능 추가, 성능 개선, 보안 패치를 위해 지속적으로 새로운 버전이 출시된다. 운영 환경에서는 서비스 중단을 최소화하기 위해 **Replica를 먼저 업그레이드한 뒤 Failover를 수행하는 방식**을 사용한다.

---

## 센티널 구성의 레디스 버전 업그레이드

Sentinel 환경에서는 Master를 먼저 업그레이드하면 서비스가 중단될 수 있다. 따라서 **Replica를 먼저 업그레이드한 뒤 Failover를 수행하는 순서**를 따른다.

업그레이드 절차는 다음과 같다.

1. Replica Redis를 종료한다.
2. Replica를 새로운 버전으로 설치하고 실행한다.
3. Replica가 Master와 정상적으로 동기화되는지 확인한다.
4. Sentinel에서 Failover를 수행하여 Replica를 새로운 Master로 승격한다.
5. 기존 Master를 종료한 뒤 새로운 버전으로 업그레이드한다.
6. 업그레이드된 Redis가 Replica로 정상 동작하는지 확인한다.

```
기존 상태

Master(v6)
   │
Replica(v6)

↓

Replica 업그레이드

Master(v6)
   │
Replica(v7)

↓

Failover

Master(v7)
   │
Replica(v6)

↓

기존 Master 업그레이드

Master(v7)
   │
Replica(v7)
```

### 🤔 왜 Replica부터 업그레이드할까?

Master를 먼저 종료하면 서비스가 중단될 수 있다. 하지만 Replica를 먼저 업그레이드한 뒤 Failover를 수행하면 새로운 버전의 Replica가 Master 역할을 수행하므로 다운타임을 최소화할 수 있다.

---

## 클러스터 구성의 레디스 버전 업그레이드

Redis Cluster도 Sentinel과 동일하게 **Replica부터 업그레이드**한다.

다만 Cluster는 각 Master가 서로 독립적으로 슬롯을 관리하기 때문에 노드 단위로 순차적으로 업그레이드를 진행한다.

업그레이드 절차는 다음과 같다.

1. Replica 노드를 새로운 버전으로 업그레이드한다.
2. Replica가 정상적으로 동기화되었는지 확인한다.
3. Failover를 수행하여 Replica를 Master로 승격한다.
4. 기존 Master를 새로운 버전으로 업그레이드한다.
5. 모든 Master에 대해 동일한 작업을 반복한다.

```
Master1(v6) ─ Replica1(v6)

↓

Replica1(v7)

↓

Failover

Master1(v7) ─ Replica1(v6)

↓

기존 Master 업그레이드

Master1(v7) ─ Replica1(v7)
```

### 🤔 Cluster에서 한 번에 모든 노드를 업그레이드하면 안 될까?

모든 노드를 동시에 종료하면 Cluster가 정상적으로 슬롯을 관리하지 못해 서비스 장애가 발생할 수 있다. 따라서 노드를 하나씩 순차적으로 업그레이드하여 Cluster가 항상 정상 상태를 유지하도록 해야 한다.

---

# 13.3 레디스 운영 가이드

Redis는 대부분 메모리에 데이터를 저장하기 때문에 작은 설정 하나가 성능이나 장애에 큰 영향을 줄 수 있다. 운영 환경에서는 적절한 설정과 지속적인 모니터링이 매우 중요하다.

---

## 장애 또는 성능 저하를 유발할 수 있는 레디스의 설정 항목

### maxmemory

Redis가 사용할 최대 메모리를 지정하는 옵션이다.

```
maxmemory 4gb
```

`maxmemory`를 설정하지 않으면 Redis는 시스템 메모리를 계속 사용하게 된다. 메모리가 부족해지면 OOM(Out Of Memory)이 발생하거나 운영체제가 Redis 프로세스를 종료할 수도 있다.

---

### maxmemory-policy

메모리가 가득 찼을 때 어떤 데이터를 제거할지 결정하는 정책이다.

대표적인 정책은 다음과 같다.

| 정책 | 설명 |
| --- | --- |
| noeviction | 데이터를 삭제하지 않고 Write 요청을 거부 |
| allkeys-lru | 모든 Key 중 가장 오래 사용하지 않은 Key 삭제 |
| allkeys-lfu | 사용 빈도가 가장 낮은 Key 삭제 |
| volatile-lru | TTL이 있는 Key만 대상으로 LRU 적용 |
| volatile-ttl | TTL이 가장 짧은 Key부터 삭제 |

### 🤔 캐시 서버에서는 어떤 정책을 사용할까?

캐시 용도의 Redis는 오래된 캐시를 삭제하는 것이 서비스 중단보다 낫다. 따라서 일반적으로 `allkeys-lru` 또는 `allkeys-lfu`를 많이 사용한다.

---

### stop-writes-on-bgsave-error

기본값은 `yes`이다.

RDB 저장에 실패하면 Redis는 데이터 보호를 위해 모든 Write 작업을 중단한다.

캐시 서버에서는 백업 실패보다 서비스 지속이 중요한 경우가 많으므로 상황에 따라 `no`로 변경하기도 한다.

```
stop-writes-on-bgsave-error no
```

---

### THP(Transparent Huge Pages)

Linux의 THP 기능은 메모리 관리에는 도움이 될 수 있지만 Redis에서는 성능 저하를 유발하는 경우가 많다.

운영 환경에서는 THP를 비활성화하는 것을 권장한다.

---

### overcommit_memory

Redis는 `fork()`를 이용해 RDB와 AOF Rewrite를 수행한다.

Linux의 `vm.overcommit_memory`가 적절하게 설정되어 있지 않으면 백업이 실패할 수 있다.

운영 환경에서는 일반적으로 다음 값을 사용한다.

```bash
vm.overcommit_memory = 1
```

---

# 레디스 운영 및 성능 최적화

Redis는 대부분의 명령어가 매우 빠르지만, 잘못된 명령어나 설정을 사용하면 성능 저하가 발생할 수 있다. 운영 환경에서는 불필요한 CPU 사용과 메모리 낭비를 줄이고, 블로킹이 발생하지 않도록 주의해야 한다.

---

## O(N) 명령어 사용을 최소화한다.

Redis는 단일 스레드(Single Thread)로 명령을 처리한다. 따라서 시간이 오래 걸리는 명령 하나가 실행되는 동안 다른 요청은 모두 대기하게 된다.

대표적인 O(N) 명령어는 다음과 같다.

| 명령어 | 설명 |
| --- | --- |
| KEYS | 모든 Key 조회 |
| HGETALL | Hash 전체 조회 |
| LRANGE | 큰 List 조회 |
| SMEMBERS | Set 전체 조회 |
| ZRANGE | 큰 Sorted Set 조회 |
| FLUSHALL | 모든 데이터 삭제 |

가능하면 이러한 명령은 운영 환경에서 사용하지 않는 것이 좋다.

---

## KEYS 대신 SCAN을 사용한다.

`KEYS` 명령은 모든 Key를 한 번에 조회하기 때문에 데이터가 많을수록 Redis를 오래 점유하게 된다.

```bash
KEYS user:*
```

운영 환경에서는 `SCAN` 명령을 사용하는 것이 권장된다.

```bash
SCAN 0 MATCH user:* COUNT 100
```

`SCAN`은 데이터를 조금씩 조회하므로 서비스에 미치는 영향이 훨씬 적다.

### 🤔 SCAN도 모든 Key를 조회하는데 왜 더 안전할까?

`SCAN` 역시 전체 Key를 조회하지만, 한 번에 모든 데이터를 가져오지 않고 여러 번 나누어 조회한다. 따라서 Redis가 다른 요청도 함께 처리할 수 있어 서비스 지연이 크게 줄어든다.

---

## DEL 대신 UNLINK를 사용한다.

큰 Hash나 List를 `DEL`로 삭제하면 삭제 작업이 끝날 때까지 Redis가 다른 명령을 처리하지 못할 수 있다.

```bash
DEL cache:user:100
```

Redis 4.0부터는 `UNLINK`를 사용할 수 있다.

```bash
UNLINK cache:user:100
```

`UNLINK`는 Key를 논리적으로 먼저 제거한 뒤 실제 메모리 해제는 백그라운드에서 수행한다.

대용량 데이터를 삭제할 때는 `UNLINK` 사용이 권장된다.

---

## 메모리 단편화를 관리한다.

Redis는 데이터를 반복적으로 생성하고 삭제하면서 메모리 단편화(Fragmentation)가 발생할 수 있다.

메모리 단편화가 심해지면 실제 사용 중인 메모리보다 더 많은 메모리를 점유하게 되어 성능 저하가 발생할 수 있다.

Redis는 Active Defragmentation 기능을 제공한다.

```
activedefrag yes
```

단편화가 심한 경우 자동으로 메모리를 정리하여 효율을 높일 수 있다.

---

## 적절한 자료구조를 선택한다.

같은 데이터를 저장하더라도 자료구조 선택에 따라 성능 차이가 발생한다.

예를 들어

- 단순 문자열 → String
- 객체 형태 → Hash
- 순위 기능 → Sorted Set
- 큐 → List 또는 Stream

처럼 목적에 맞는 자료구조를 사용하는 것이 중요하다.

---

## Pipeline을 활용한다.

여러 명령을 순차적으로 전송하면 네트워크 왕복(RTT)이 반복적으로 발생한다.

Pipeline을 사용하면 여러 명령을 한 번에 전송하여 네트워크 비용을 줄일 수 있다.

특히 대량의 데이터를 저장하거나 조회하는 작업에서 성능 향상 효과가 크다.

---

# 레디스 모니터링

Redis를 운영할 때는 단순히 서버가 살아있는지만 확인하는 것이 아니라 주요 지표를 지속적으로 모니터링해야 한다.

---

## Memory

가장 중요한 모니터링 대상이다.

주요 지표

| 지표 | 설명 |
| --- | --- |
| used_memory | Redis가 실제 사용하는 메모리 |
| used_memory_rss | 운영체제가 할당한 실제 메모리 |
| maxmemory | 최대 메모리 설정값 |
| mem_fragmentation_ratio | 메모리 단편화 비율 |

`mem_fragmentation_ratio`가 지속적으로 높다면 메모리 단편화를 의심해 볼 수 있다.

---

## Connected Clients

현재 Redis에 연결된 클라이언트 수를 의미한다.

갑자기 연결 수가 증가하면

- Connection Leak
- 비정상적인 트래픽
- 애플리케이션 오류

등을 의심할 수 있다.

---

## Cache Hit Ratio

Redis 캐시가 얼마나 효율적으로 사용되고 있는지 확인하는 지표이다.

다음 두 값을 이용해 계산할 수 있다.

- keyspace_hits
- keyspace_misses

Hit Ratio가 낮다면 캐시 전략을 다시 검토하는 것이 좋다.

---

## Commands per Second

Redis가 초당 처리하는 명령 수이다.

갑작스럽게 증가하거나 감소한다면 서비스 부하나 장애 여부를 확인해야 한다.

---

## Evicted Keys

메모리가 부족하여 Redis가 강제로 삭제한 Key 개수이다.

Evicted Keys가 계속 증가한다면

- maxmemory 설정
- maxmemory-policy
- 메모리 용량

을 점검해야 한다.

---

## Expired Keys

TTL이 만료되어 자동으로 삭제된 Key 개수이다.

Expired Keys 증가는 정상적인 현상이지만, 예상보다 지나치게 많다면 TTL 정책을 다시 확인해 볼 필요가 있다.

---

## Replication 상태

복제 환경에서는 Replica가 Master와 정상적으로 동기화되고 있는지 확인해야 한다.

특히 Replication Lag이 증가하면 장애 발생 시 최신 데이터가 손실될 가능성이 있으므로 지속적으로 모니터링해야 한다.

## Slow Log

Redis는 일정 시간 이상 수행된 명령을 Slow Log에 기록한다.

```bash
SLOWLOG GET
```

Slow Log를 확인하면 어떤 명령이 성능 저하를 유발하는지 쉽게 파악할 수 있다.

운영 환경에서는 주기적으로 확인하여 O(N) 명령이나 비효율적인 쿼리를 개선하는 것이 좋다.

---

## 📌 정리

운영 환경에서 Redis를 안정적으로 사용하려면 단순히 캐시 서버를 구축하는 것만으로는 부족하다.

- Prometheus와 Grafana를 이용해 지속적으로 모니터링하고,
- Sentinel이나 Cluster 환경에서는 Replica부터 순차적으로 업그레이드하며,
- `maxmemory`, `maxmemory-policy` 등 주요 설정을 서비스 특성에 맞게 구성해야 한다.
- 또한 `SCAN`, `UNLINK`, Pipeline 등을 활용하여 성능 저하를 예방하고, Memory, Cache Hit Ratio, Replication, Slow Log 등의 핵심 지표를 꾸준히 확인하는 것이 안정적인 Redis 운영의 핵심이다.
