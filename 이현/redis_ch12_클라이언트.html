01 · Client Handling

레디스는 TCP 포트 또는 Unix Socket으로 클라이언트 연결을 받는다

일반적인 서비스 환경에서는 TCP 포트를 사용한다. 같은 서버 내부에서 통신하는 경우에는 설정 파일에서 Unix Socket 관련 매개변수를 설정해 원하는 경로에 소켓 파일을 생성하고 권한을 지정할 수 있다.

01-1 · Multiplexing & Non Blocking I/O

하나의 스레드가 여러 소켓을 감시한다

레디스는 멀티플렉싱 방식을 사용한다. 하나의 통신 채널을 통해 여러 데이터 스트림을 처리할 수 있고, 하나의 스레드에서 여러 소켓을 감시하면서 이벤트 발생 여부를 계속 확인한다.

여러 소켓 감시

읽기 가능한 파일 이벤트가 발생하면 해당 클라이언트에서 전송한 쿼리를 수집하고 처리한다.

블로킹 회피

많은 클라이언트 요청을 동시에 처리할 때 특정 클라이언트 때문에 전체가 멈추는 문제를 줄인다.

효율적인 다중 클라이언트 지원

스레드마다 클라이언트를 할당하지 않아도 높은 동시성을 처리할 수 있다.

논블로킹 I/O

논블로킹 I/O는 I/O 작업이 완료될 때까지 기다리지 않고 다른 작업을 처리하는 방식이다. 그래서 레디스는 클라이언트 요청을 비동기적으로 처리하며 다수의 요청을 동시에 처리할 수 있다.

01-2 · TCP_NODELAY

작은 데이터도 지연 없이 보내기 위해 TCP_NODELAY를 사용한다

레디스는 클라이언트 커넥션을 생성할 때 TCP_NODELAY 옵션을 사용한다. 소켓은 작은 데이터라도 버퍼링하지 않고 가능한 한 빨리 패킷으로 전송하려고 시도한다.

사용 이유

작은 데이터 조각을 실시간으로 전송해야 하는 경우에 유리하다. 클라이언트 연결 지연을 최소화할 수 있다.

트레이드오프

지연은 줄어들지만 더 많은 패킷이 발생할 수 있어 네트워크 대역폭 사용량은 늘어날 수 있다.

복제 연결에서는 repl-disable-tcp-nodelay로 제어한다

# 기본값: 지연 시간 최소화
repl-disable-tcp-nodelay no
설정동작장점단점
no마스터와 복제본 간 데이터 지연을 최소화복제본에서 데이터를 더 빨리 확인 가능복제를 위해 더 많은 대역폭 사용
yes복제본에 데이터를 전송할 때 더 작은 수의 패킷과 대역폭 사용대역폭 절약최대 약 40ms 지연 발생 가능
실무 포인트레디스는 지연 시간을 최소화하기 위해 기본값을 no로 둔다. 다만 대규모 트래픽이 있거나 마스터와 복제본의 거리가 멀다면 yes로 변경하는 것이 도움이 될 수 있다.
01-3 · maxclients

연결 수가 maxclients에 도달하면 새로운 접속을 거부한다

클라이언트가 초기화되면 레디스는 현재 클라이언트 수와 maxclients 설정값을 비교한다. 설정값에 도달하면 새로운 클라이언트 접속을 거부한다.

02 · Client Buffer Limit

응답을 못 읽는 클라이언트는 서버 메모리를 계속 사용한다

레디스는 클라이언트에 반환할 데이터를 임시로 저장하기 위해 각 클라이언트마다 출력 버퍼(Output Buffer)를 생성한다.

Redis 응답 생성
→
Output Buffer
→
Client 읽기

출력 버퍼는 레디스가 반환할 데이터 양에 따라 가변 길이다. 하지만 클라이언트가 데이터를 처리하지 못하고 계속 서버에 요청을 보내면 출력 버퍼 크기가 계속 증가하고, 결국 메모리 사용량이 증가한다.

Hard Limit

정해진 임계치를 초과하는 순간 클라이언트 연결을 즉시 종료한다.

Soft Limit

정해진 임계치를 일정 시간 이상 유지하면 클라이언트 연결을 종료한다.

클라이언트 종류별로 다르게 적용레디스에서는 일반 클라이언트, Pub/Sub 클라이언트, 복제본을 위한 출력 버퍼 크기 제한을 모두 다르게 적용한다.
02-1 · Pub/Sub & Query Buffer

Pub/Sub에서는 느린 구독자의 출력 버퍼가 특히 문제가 된다

Pub/Sub에서 발행자가 메시지를 발행하면 해당 메시지는 모든 구독자에게 전달된다. 구독자가 메시지를 따라가지 못하면 해당 구독자의 출력 버퍼가 계속 증가할 수 있다.

03 · Client Eviction

Redis 7부터는 클라이언트가 쓰는 총 메모리도 제한할 수 있다

클라이언트 연결 수가 증가하면 메모리 사용량도 증가한다. 클라이언트 연결이 메모리를 과다 사용하면 OOM이 발생하거나 데이터 이빅션을 유발할 수도 있다.

Redis 7 이전

maxmemory-policy로 전체 메모리 상황을 관리했다. 클라이언트 메모리만 직접 제한하기는 어려웠다.

Redis 7 이후

maxmemory-clients를 사용해 연결된 모든 클라이언트의 최대 총 메모리 사용량을 정의할 수 있다.

# redis.conf 또는 CONFIG SET으로 변경 가능
maxmemory-clients 1gb

가장 많은 메모리를 쓰는 연결부터 해제한다

Eviction

임계치에 도달하면 가장 많은 메모리를 사용하는 클라이언트 연결부터 해제해 메모리를 확보한다.

Client A 제거

이 동작이 클라이언트 이빅션이다.

예외복제 연결에 사용되는 복제본과 마스터 커넥션은 영향을 받지 않는다. 복제 과정에서 메모리 사용량이 커도 자동으로 끊어지지 않는다.
제외 처리모니터링과 알림을 보내는 중요한 클라이언트처럼 특정 연결은 이빅션 대상에서 제외할 수 있다.
04 · Timeout & TCP Keepalive

Timeout은 유휴 연결 정리, Keepalive는 비정상 연결 감지다

레디스 서버에 클라이언트가 연결되면 장기간 커맨드를 수행하지 않아도 기본적으로 연결이 계속 유지된다.

05 · Pipelining

RTT가 크면 Redis가 빨라도 전체 처리량은 낮아진다

레디스 서버와 클라이언트는 네트워크를 통해 연결되어 있다. 요청과 응답 사이의 왕복 시간인 RTT는 성능에 큰 영향을 끼친다.

예시

250ms

RTT가 250ms라면 Redis 서버가 초당 10만 개 요청을 처리할 수 있어도 네트워크 왕복 때문에 초당 최대 4개 요청 수준으로 제한될 수 있다.

해결 방향

네트워크 통신 소요 시간을 줄이면 레디스 성능을 크게 향상시킬 수 있다.

파이프라이닝이란?

클라이언트가 응답을 기다리지 않고 연속적으로 여러 커맨드를 레디스 서버에 보낼 수 있도록 하는 기능이다. 일반적으로는 하나의 커맨드를 보내고 결과를 받은 뒤 다음 커맨드를 보내지만, 파이프라이닝을 사용하면 여러 커맨드를 일괄 처리할 수 있다.

SET user:1 hyun
GET user:1
INCR view:1
EXPIRE user:1 60

레디스 서버가 클라이언트에 응답하기 위해 소켓 I/O를 수행할 때 운영체제 커널 영역의 read(), write() 시스템 콜을 호출한다. 이 과정에서 발생하는 레이턴시가 레디스 서버에서 데이터를 찾고 반환하는 과정보다 클 수 있다.

단일 read()

파이프라인으로 들어온 여러 명령을 단일 read() 시스템 콜로 읽을 수 있다.

단일 write()

여러 응답을 단일 write() 시스템 콜로 전달할 수 있어 처리량이 증가한다.

4시간 → 3분 33초

책 예시처럼 대량 작업에서는 파이프라이닝만으로도 처리 시간이 크게 줄어들 수 있다.

처리량 증가파이프라이닝에 속한 커맨드가 많아질수록 초당 수행되는 총 쿼리 수는 거의 선형적으로 증가한다.
05-2 · Caution

파이프라인은 트랜잭션이 아니고 원자성을 보장하지 않는다

너무 많이 보내면 안 됨

한 번에 너무 많은 쿼리를 보내면 대역폭 한계로 인해 속도가 저하될 수 있다.

Query Buffer 제한

쿼리 버퍼 제한에 걸려 오류가 발생할 수 있다.

배치 크기 조절

일정한 개수로 나누어 배치 형태로 보내는 것이 좋다. 배치 크기는 테스트를 통해 결정한다.

원자성 보장 X

레디스가 파이프라인으로 들어온 명령을 처리할 때 하나의 파이프라인에 속해 있더라도 원자성을 보장하지 않는다. 파이프라이닝은 여러 커맨드를 동시에 보낼 수 있는 방법일 뿐, 다른 클라이언트의 접근을 차단하지 않는다.

06 · Client Side Caching

Redis 부하 감소

Redis에 접근하지 않고도 데이터를 반환하므로 서버 부하가 줄어든다.

적합한 데이터

자주 요청되지만 드물게 변경되는 데이터에 적합하다.

예시SNS에 한 번 업로드한 사용자 게시물은 자주 읽히지만 수정은 드물 수 있다. 이런 데이터는 클라이언트 사이드 캐싱 후보가 될 수 있다.
주의클라이언트 로컬 캐싱은 데이터 정합성을 고려해야 한다. Redis 데이터가 변경되었는데 클라이언트가 오래된 값을 들고 있으면 잘못된 응답을 반환할 수 있다.

07 · Summary

클라이언트 관리는 네 가지 관점으로 보면 된다

1. 연결 처리

Redis는 하나의 이벤트 루프에서 멀티플렉싱과 논블로킹 I/O를 사용해 수많은 클라이언트 연결을 처리한다. TCP_NODELAY와 maxclients로 지연 시간과 연결 수를 제어한다.

2. 메모리 보호

느린 클라이언트가 서버 메모리를 과도하게 사용하는 것을 막기 위해 Output Buffer, Query Buffer, Hard/Soft Limit, Client Eviction 기능을 제공한다.

3. 네트워크 최적화

파이프라이닝은 여러 명령을 한 번에 전송해 RTT와 read/write 시스템 콜을 줄인다. 이를 통해 처리량을 크게 향상시킨다.

4. Redis 접근 최소화

Client Side Caching은 자주 조회되고 드물게 변경되는 데이터를 애플리케이션 메모리에 저장한다. Tracking을 통해 캐시 정합성도 유지할 수 있다.

최종 정리

Redis 클라이언트 관리는 ① 연결을 효율적으로 처리하고 ② 메모리 사용을 제어하며 ③ 네트워크 비용을 줄이고 ④ Redis 접근 자체를 최소화하는 기술들의 집합이다.
